# Git

The workspace repository and its pull requests: status, branches, history and diffs through the git CLI, branch management, merges, rebases, stashes, tags, blame, a conflict editor and worktrees on top, and pull requests with their checks through the GitHub CLI (`gh`), signed in as you, so Quiver stores no GitHub token, with a new one's description drafted from git. The plans it was built from are in [docs/plans/git-runner-queues.md](../../../../docs/plans/git-runner-queues.md), for branch management lane A of [docs/plans/agent-git-kube-cli.md](../../../../docs/plans/agent-git-kube-cli.md), and for blame, the conflict editor, pull request drafts and worktrees [docs/plans/git-blame-conflicts-pr-worktrees.md](../../../../docs/plans/git-blame-conflicts-pr-worktrees.md).

## Local repository

The workspace folder's repository, through the `git` CLI found on PATH ([`local.ts`](local.ts), commands in [`commands-local.ts`](commands-local.ts)). Every call is its own git process run in the repository's root folder with stdin closed, `GIT_TERMINAL_PROMPT=0` and no optional locks, so nothing waits on a prompt and a status never fights a git running in your terminal. Running at the root (`rev-parse --show-toplevel`) is what makes paths mean one thing everywhere: `status` and `diff` print them relative to the root whatever the folder, so `stage`, `unstage`, `diff` and `log` take them that way too, also when the workspace is a subfolder of the repository. Git is asked for NUL-separated output (`status --porcelain=v2 --branch -z`, `log` with `%x00` fields, `diff --raw --numstat -z`), parsed by `packages/core/src/git-parse.ts`, so paths with spaces or quotes come through intact. Nothing is stored: git is the only state.

| Command | What it gives or does |
| --- | --- |
| `git.status` | Branch (null when detached), HEAD (null before the first commit), upstream with ahead/behind, the operation in progress (merge, rebase, cherry-pick, revert) and the changed files with their index and worktree codes (`.` unchanged, `?` untracked). An untracked folder is one entry (`new/`), as git itself lists it, rather than every file in it. `files: false` leaves the files out (an empty list): git then neither looks for untracked files nor goes into submodules, most of a status's cost in a big repository. `worktree: { linked, mainPath }` says whether the workspace is a linked worktree and where the main worktree is (see [Worktrees](#worktrees)). |
| `git.branch.list` | Local and remote-tracking branches, newest first, with upstream, ahead/behind, head commit, subject and date. `merged`: all its commits are in the default branch (`origin/HEAD`, else a local `main` or `master`), or in the current branch when there is none (`for-each-ref --merged`); never set on that branch, its remote copies or the current branch. `gone`: its upstream was deleted on the remote and pruned by a fetch. `worktreePath`: the other worktree a local branch is checked out in (`%(worktreepath)`), which git will not check it out beside; a git before 2.23 does not know that field, and then the list comes without it. |
| `git.log` | `{ commits, hasMore }`, newest first, of HEAD or `ref`, optionally only commits touching `path`; paged with `limit` and `skip`. |
| `git.diff` | Per-file status, line counts and unified patch: working tree against the index by default, `staged` for the index against HEAD, `from` for the working tree (or index) against a ref, `from` and `to` between two refs. `statOnly` leaves the patches out; a patch over 512 KB, or past the 32 MB output cap, is left out and the file marked `truncated`. |
| `git.show` | `{ commit, files }`: one commit and its changes against its first parent (a root commit against the empty tree). |
| `git.fetch` | `git fetch --prune` of the default remote or `remote`; only remote-tracking refs change. |
| `git.checkout` | Switches to a branch, tag or commit; fails rather than overwrite local changes. A branch another worktree has checked out is refused with a message naming that worktree (`details.reason: 'checked-out-elsewhere'`, `details.path`). |
| `git.branch.create` | A branch at HEAD or `from`, switched to unless `checkout: false`. |
| `git.stage`, `git.unstage` | `git add --all` / `git restore --staged` of paths (`git rm --cached` before the first commit). |
| `git.commit` | Commits the index with the message (passed on stdin, trimmed like an editor would but with `#` lines kept), `amend` to replace the last commit; hooks run. Gives back the new commit. |
| `git.pull` | `git pull --no-edit` of the upstream or `remote` and `branch`, per the repository's own pull settings. |
| `git.push` | Pushes the current branch, or `remote` and `branch`; `setUpstream` (origin and the current branch by default), `forceWithLease`. `branch` is a name, never a refspec: `:main`, `+x:main`, `main:other` and patterns are refused, so nothing is deleted or forced through it. |

The mutating commands and fetch give back the new status (pull and push with git's output as well), and emit `git.changed` straight away. A watcher on HEAD, the index and the operation markers in the git dir, and on `refs`, `packed-refs` and `worktrees` in the common dir, emits `git.changed` too, debounced by 250 ms, so a commit or checkout made in a terminal reaches the view: `status` when HEAD or the index moved, `branches` when HEAD or a ref did, `worktrees` when a worktree was added, removed, locked, unlocked or switched branch. In the main worktree both dirs are `.git`; in a linked worktree the git dir is `<common>/worktrees/<name>` (see [Worktrees](#worktrees)). Edits to working files are not watched. The watcher starts when the workspace opens, or with the first git command once the folder has become a repository, and stops when it closes.

Refs, branch names, remotes and paths are refused when they start with `-` (`GitArgSchema`), and paths always follow `--`, so no input can become a git option such as `--output=<file>`. `remote`, for fetch, pull and push, must be one of the repository's configured remotes: git itself also takes a URL or a folder there, which would let an agent's read-only fetch pull any repository the user's credentials or disk can reach into `FETCH_HEAD`. For fetch, pull and push made by an agent, `GCM_INTERACTIVE=never` keeps Git Credential Manager from opening a sign-in window the agent cannot see (the call fails instead); from the UI the window still opens, which is how a first sign-in happens. When git is not on PATH the commands fail with `NOT_FOUND` and `details.reason: 'no-git'`; in a folder that is not a repository with `NOT_FOUND` and `details.reason: 'not-a-repo'`; a git failure is `REQUEST_FAILED` with git's own message. Git runs with `LANGUAGE=en`, so its messages are in English whatever the user's locale, and the few the commands read ("not fully merged", a push's `[rejected]`) are found.

Agents may call `git.status`, `git.branch.list`, `git.log`, `git.diff`, `git.show` and `git.fetch`. `git.checkout`, `git.branch.create`, `git.stage`, `git.unstage`, `git.commit`, `git.pull` and `git.push` are mutating: they get what the agent permissions say (refused in the default read-only mode, asked about in ask mode).

### Managing the repository

Branches, merges and rebases with the operation they leave in progress, commits picked, reverted or reset to, stashes, tags, discarding and a file at a ref ([`commands-manage.ts`](commands-manage.ts), over the same `local.ts`). The same rules hold: one git process per step at the repository root, `GitArgSchema` on every ref, name and path, paths after `--`, `GCM_INTERACTIVE=never` on network calls an agent makes, `git.changed` straight after every write, and the new status (or the result below) given back. Branch and tag names must be plain names: no refspec (`:x`, `+x`, `a:b`, `*`, `^`), no `refs/…` and not `HEAD`.

Merge, rebase, cherry-pick, revert, stash apply and the continue, skip and abort of the operation in progress give back `{ output, conflicts, status }`. Stopping on conflicts is a success that lists the conflicted paths, with the operation left in progress (`status.operation`); any other failure is `REQUEST_FAILED` with git's message. When such a failure still leaves the operation in progress (a hook refused the commit, or a cherry-pick came out empty), the message says to continue, skip or abort it, and `details` carry `reason: 'operation-in-progress'`, the `operation` and the new `status`. The change is announced whether the command succeeded or not. The operation in progress comes from git's marker files (`MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge`, `rebase-apply`), and from `sequencer/`, which a cherry-pick or revert of several commits keeps until the last one, also after the one it stopped on was committed by hand; the watcher follows all of them. They run with `GIT_EDITOR=:` and `GIT_SEQUENCE_EDITOR=:` (`:` is git's own "no editor"), so a continue keeps git's prepared message and nothing ever waits on an editor; no command starts an interactive rebase. A merge, rebase, cherry-pick, revert or stash apply is refused while another operation or unresolved conflicts are in the way (`details.reason: 'operation-in-progress'` or `'unresolved'`), so git's own refusal is never mistaken for that command's conflicts. They get 180 seconds rather than a read's 30, since they replay commits and run their hooks.

| Command | What it gives or does |
| --- | --- |
| `git.branch.delete` | `git branch -d`, `-D` with `force`. Refuses the current branch (`details.reason: 'current-branch'`), and a branch another worktree has checked out with a message naming it (`'checked-out-elsewhere'`, `details.path`). When git finds the branch not merged into its upstream or HEAD, it still goes if its commits are in the default branch (what `merged` in the list means, so a branch merged into `main` is deleted from any branch without force), but never the default branch itself on that ground (neither `main` nor, when the default is `origin/main`, the local `main`); otherwise `INVALID_INPUT` with `details.reason: 'not-merged'`, and `force` drops it, its commits then only in the reflog. |
| `git.branch.deleteRemote` | `git push --delete <remote> refs/heads/<name>` (the full ref, so a tag of that name never goes), which also drops the remote-tracking branch. `remote` must be a configured remote. The remote's default branch is refused (`details.reason: 'default-branch'`), read from `refs/remotes/<remote>/HEAD` or, when the clone did not record it, from `git ls-remote --symref`. |
| `git.branch.rename` | `git branch -m [from] to`; the current branch when `from` is left out. The upstream stays; the branch on the remote keeps its name. |
| `git.branch.setUpstream` | `--set-upstream-to=<upstream>` of `branch` (the current one by default), or `--unset-upstream` with `upstream: null`. Nothing is fetched or pushed. |
| `git.merge` | `git merge --no-edit` of a branch, tag or commit into the current branch; `mode` `ff`, `no-ff`, `ff-only` or `squash` (staged, not committed), `message` passed as `--message=<text>`. |
| `git.rebase` | `git rebase <onto>`, never interactive. |
| `git.operation.continue`, `git.operation.skip`, `git.operation.abort` | `git <merge, rebase, cherry-pick or revert> --continue`, `--skip`, `--abort`, for the operation in progress (`details.reason: 'no-operation'` when there is none). Continue is refused while conflicts are unresolved (`'unresolved'`), and a merge has no skip. A rebase or cherry-pick that stops on the next commit's conflicts lists them. |
| `git.cherryPick` | `git cherry-pick` of up to 100 commits, in the order given. |
| `git.revert` | `git revert --no-edit` of a commit (a merge commit fails with git's message). |
| `git.reset` | `git reset --soft`, `--mixed` or `--hard <ref> --`. |
| `git.stash.list` | The stashes, newest first: `index` (the N of `stash@{N}`), hash, message (or git's WIP line), the branch it was made on and the date. |
| `git.stash.show` | `{ stash, files }`: its changes against the commit it was made on, as `git.diff` gives them, then the untracked files it holds (its third parent) as added. |
| `git.stash.push` | `git stash push`, with `message` (as `--message=<text>`), `includeUntracked`, and `paths` after `--`, each as `:(literal)<path>` so a name like `[id].tsx` is never read as a glob. Nothing to stash is `INVALID_INPUT` with `details.reason: 'nothing-to-stash'`: git itself exits 0, so the command checks whether `refs/stash` moved. |
| `git.stash.apply` | `git stash apply <hash>`, or `pop stash@{index}` with `pop: true` (checked against the hash again just before); conflicts are listed, and a pop that stops on them keeps the stash. A stash index that does not exist is `NOT_FOUND`. With `hash` (from the list), a stash@{index} that is another stash by now is refused (`details.reason: 'stash-moved'`); the panel always sends it. |
| `git.stash.drop` | `git stash drop`; gives back the stashes left, which move up by one. Takes `hash` as apply does. |
| `git.discard` | Throws changes away: paths the status lists as untracked go to `git clean --force` (with `-d` for a folder entry such as `new/`), every other path to `git restore --worktree` (back to the index), or with `staged: true` to `git restore --source=HEAD --staged --worktree` (back to HEAD; a staged rename's old path goes back too). The restore runs first, so a path git does not know fails the call before anything is deleted; a file inside an untracked folder entry, or an ignored one, is never deleted. Paths are literal (`GIT_LITERAL_PATHSPECS=1`), so `n[x].txt` never takes `nx.txt` with it. |
| `git.tag.list` | The tags, newest first: name, the commit it points at (an annotated tag's target), annotated or not, its message's first line (a lightweight tag's commit subject) and date. |
| `git.tag.create` | A lightweight tag of HEAD or `ref`, or an annotated one with `message`, which goes on stdin (`--file=-`, trimmed like the commit message). Gives back the tag. |
| `git.tag.delete` | `git tag -d`; a pushed tag stays on the remote. Gives back the tags left. |
| `git.tag.push` | `git push <remote> refs/tags/<name>` to a configured remote; a different tag of that name there makes it fail rather than move. |
| `git.file.show` | A file's content at `ref`, or in the index with `index: true`, read as the stored blob (`cat-file`, no line-ending or filter conversion). Over 2 MB it comes back `tooLarge`, and binary (a NUL in its first 8000 bytes, git's own test) as `binary`, both without content. A folder, a missing path, a ref with a colon (it would move part of the ref into the path) and a ref given with `index` are refused. |

The watcher announces a stash with `git.changed` reason `stashes` when `refs/stash` moves; dropping an older stash only rewrites its reflog, so the stash commands announce it themselves.

### Blame

Who last changed each line of a file ([`commands-blame.ts`](commands-blame.ts), over the same `local.ts`).

| Command | What it gives or does |
| --- | --- |
| `git.blame` | `git blame --porcelain [-w] [<ref>] -- <path>` of the working tree's file, or of the file at `ref`, parsed by `parseBlamePorcelain` in core into `{ path, ref, lines, commits }`. Each line has its number, its text (without its line ending, a CRLF line's CR dropped), the hash of the commit that last changed it and its line number there (`originalLine`); a line not committed yet (git's all-zero hash, "Not Committed Yet") has `commit: null`. `commits` is keyed by hash and lists each commit once, however many lines it has: author, email, `authorTime` (ISO 8601), summary, the file's `path` in that commit (renames are followed), `previous` (the commit before it that held the lines and the path there, which is where "blame before this commit" goes) and `boundary` (the history stops there: a root commit). `ignoreWhitespace` adds `-w`. The repository's `.git-blame-ignore-revs` is passed as `--ignore-revs-file` when it exists; when git refuses it (a commit it names is not in this clone), the blame runs again without it, and if that fails too its error is the one given. |

The file is checked first, as `git.file.show` checks it. A path outside the repository is refused either way. At a ref the committed file is checked through `fileAt` (a missing path, a folder or a ref with a colon refused there), whatever the working tree holds; in the working tree the file on disk (a folder or a missing file refused, the last saying to give a ref; a symbolic link is not followed, as git blames the link itself). A file git has never been told about (untracked) is refused with `details.reason: 'untracked'`. Over 2 MB is refused with `details.reason: 'too-large'` and binary (a NUL in the first 8000 bytes) with `'binary'`. The path follows `--` and goes through `GitArgSchema`, as does the ref, so neither can become an option; the blame gets 120 seconds, since it walks the file's history. It is a read: nothing changes, nothing is announced, and agents may call it.

The smoke section [`parts/git/blame.ts`](../../../../src/main/smoke/parts/git/blame.ts) builds a repository in a temporary folder whose file is written by one author, changed by a second, renamed by a third and reindented by a fourth, and checks: each line given to the right commit across the rename with each commit listed once and its details (author, email, time, summary, its path then, `previous`, the root commit's `boundary`); `ignoreWhitespace` and `.git-blame-ignore-revs` looking through the reindent, and an ignore file naming a commit the clone has not got left out rather than failing; a blame at a ref; blaming the previous commit and path going back past the rename; an uncommitted line with `commit: null`; a file name with spaces and CRLF lines; an option-like path and ref, a path outside the repository (in the working tree and at a ref), a folder, a missing file (in the working tree and at a ref), an untracked file, a binary file (at a ref and in the working tree) and one over 2 MB (on disk, and at a ref while the working tree's copy is small) refused, with nothing written; and an agent calling `git_blame`.

### Resolving conflicts

One conflicted file at a time ([`commands-conflict.ts`](commands-conflict.ts), over the same `local.ts`): what each side has, and a resolution written and staged. The path must be one `git.status` lists as unmerged (`details.reason: 'not-unmerged'` otherwise), relative to the root and inside it (`'outside-repository'` for one that resolves outside, `..` included); it goes through `GitArgSchema` and after `--`, with literal pathspecs.

| Command | What it gives or does |
| --- | --- |
| `git.conflict.get` | `{ path, kind, operation, ours, theirs, base, working, labels, commits, binary, tooLarge, markerSize }`. `kind` comes from the status codes: `both-modified` (UU), `both-added` (AA), `both-deleted` (DD), `deleted-by-us` (DU), `deleted-by-them` (UD), `added-by-us` (AU) and `added-by-them` (UA). `ours`, `theirs` and `base` are index stages 2, 3 and 1 (`ls-files --unmerged -z`, then `cat-file` of each blob), null when the stage is absent; `working` is the file on disk with its markers, null when it is not there. A binary side or file (a NUL in its first 8000 bytes), a submodule's entry, or one over 2 MB sets `binary` or `tooLarge` and leaves every content null. `markerSize` is the length of the file's markers, its `conflict-marker-size` attribute (`git check-attr`), 7 by default. `labels` say what ours and theirs are, read from git's own files: in a merge the current branch and the branch `MERGE_MSG` names, with the remote for a pull ("main of github.com:o/r"; else the short `MERGE_HEAD`); in a cherry-pick the current branch and `<short hash> <subject>` of `CHERRY_PICK_HEAD`, in a revert "revert of" it; in a rebase they swap, ours being what the branch is rebased onto (the branch or tag at `rebase-merge/onto`, else its short hash) and theirs the commit being replayed (`REBASE_HEAD`) with the branch it comes from; after a stash apply, which leaves no operation, the current branch and "the incoming changes". `commits` gives the full hashes the sides come from, so a side can be blamed at it: `ours` is HEAD and `theirs` the incoming commit (`MERGE_HEAD`, `CHERRY_PICK_HEAD` or `REBASE_HEAD`), absent in a revert, whose incoming side is the reverted commit's parent rather than a commit of its own, and after a stash apply. |
| `git.conflict.resolve` | Exactly one of `content` and `take`. `content` is the whole resolved file, written as given (no line-ending change) and staged with `git add`; it is refused while it still holds a conflict, or a start, base or end marker line left over from one deleted by hand (`details.reason: 'markers'`, with `conflicts` and the marker `lines`), unless `allowMarkers: true`, and when the file is a symbolic link or a folder leads out of the repository. `take` is `ours`, `theirs` or `base`, checked out of that stage with `git checkout-index --stage=<n>` (filters and file mode as a checkout) and staged, or `delete`, `git rm`; taking a side that has no file (ours of a file deleted by us) deletes it, and `base` is refused when there is none (`'no-base'`). Gives back the new status and emits `git.changed` (`status`). |

Markers are read by `parseConflictMarkers` in `packages/core/src/git-parse.ts`: git's markers, exactly `markerSize` characters at the start of a line (seven unless the attribute says otherwise; the longer ones git writes for conflicts nested in a recursive merge's base are text), in the `merge`, `diff3` and `zdiff3` styles (the `|||||||` base section), with CRLF lines kept. A line that only looks like a marker (eight `<`, `=======` with text after it, a separator or end marker outside a conflict) is text, and so is a conflict that never closes. `renderResolution` builds a file from a choice per conflict (ours, theirs, base, both in either order, none, or text of one's own), leaving the markers of a conflict with no choice. `conflictMarkerLines` finds start, base and end marker lines left over (not a lone `=======`, which is ordinary Markdown), and `dropAddedFinalNewline` takes off the final line break git adds after the last marker when the conflict ends the file and neither side has one.

The smoke section [`parts/git/conflict.ts`](../../../../src/main/smoke/parts/git/conflict.ts) builds a repository in a temporary folder whose merge stops on a text, a binary and a deleted-by-them conflict, and checks: get with the three stages, the file with its markers, the merge's labels and the commits of both sides, deleted-by-them with no theirs, a binary file without contents, and the refusals of a path with no conflict, one outside the repository and an option-like one; resolve refusing content that still has markers and both or neither of content and take, then writing and staging content (with its `git.changed`), refusing the path once resolved, take ours of the binary file and delete of the deleted one, and the merge continuing; then a rebase whose labels and stages swap (theirs the replayed commit), agents reading the conflict while resolve is gated and changes nothing, `allowMarkers` writing the markers as they are, and take theirs keeping the replayed commit's side before the rebase continues; a cherry-pick's labels with markers lengthened by `conflict-marker-size` (in `.git/info/attributes`), content refused for those markers and for a leftover end marker while seven-character ones are text; a revert's labels, with no incoming commit, and take base; a stash apply conflict, with no operation, resolved by take theirs; and a rename on both sides giving both-deleted, added-by-us and added-by-them, resolved by delete, keep and taking the side with no file, with base refused.

### Worktrees

Several branches checked out at once, each in a folder of its own (`git worktree`; [`commands-worktree.ts`](commands-worktree.ts), over `local.ts`). The repository's main worktree holds `.git`; a linked one has a `.git` file pointing at its own git dir, `<common>/worktrees/<name>`, where its HEAD, index and operation markers live, while refs, the stash and the list of worktrees stay in the common dir. Everything above works in a linked worktree opened as a workspace: commands run at its root (`rev-parse --show-toplevel`), the operation in progress is read from its own git dir, so a merge stopped there is not the main worktree's, stashes are shared as git shares them, and the watcher watches both dirs (and creates or drops its watch on `worktrees` as git makes and deletes that folder with the first and last linked worktree).

| Command | What it gives or does |
| --- | --- |
| `git.worktree.list` | `git worktree list --porcelain -z`: every worktree, the main one first, with `path`, `head` (null before the first commit or in a bare repository), `branch` (null when detached), `detached`, `bare`, `locked` with `lockReason`, `prunable` with `prunableReason` (its folder is gone), `main` and `current` (the one the workspace is in). A git before 2.36 has no `-z`; its line-per-attribute output is read instead. |
| `git.worktree.add` | `git worktree add`, with one of `branch` (an existing branch, which must not be checked out in another worktree; a branch only a remote has becomes a local one tracking it, as git does), `newBranch` (`-b`, at `from`, default HEAD) or `detach` (at `from`). `path` is absolute or relative to the folder holding the main worktree; by default `<that folder>/<repository name>.worktrees/<branch with / as ->`, so worktrees sit together beside the repository. A folder inside any worktree, a file, and a folder that is not empty are refused. Gives back the new worktree; 180 seconds, since it checks out every file and runs the post-checkout hook. |
| `git.worktree.remove` | `git worktree remove [--force]`; the branch stays. Refuses the main worktree (`details.reason: 'main-worktree'`), the one the workspace is in (`'current-worktree'`), one open as another workspace (`'open-workspace'`) and a locked one (`'locked'`). With changes or untracked files git refuses, which comes back as `'dirty'`, and `force` removes it anyway. Gives back the worktrees left. |
| `git.worktree.lock`, `git.worktree.unlock` | `git worktree lock [--reason=<reason>]` / `unlock`, so prune and remove leave a worktree alone (one on a removable disk); the main worktree cannot be locked. Give back the worktrees. |
| `git.worktree.prune` | `git worktree prune --verbose`: forgets the worktrees whose folder was deleted by hand, unless locked. `{ pruned, worktrees }`, `pruned` naming git's record of each one removed. |

Every folder a caller gives is made absolute (`path.resolve` from the folder holding the main worktree) and, for remove, lock and unlock, must be one `git worktree list` names (compared as given, then by its real path, so a junction, a link or an 8.3 short name finds it too); that listed path is what reaches git, after `--`. Whether the workspace is a linked worktree is read from its git dir and common dir, both taken by their real path: git prints the git dir resolved, but the main worktree's common dir as `.git` beside the folder as opened, so a workspace opened through a junction or with a lower-case drive letter would otherwise look linked. Branch names are plain names as for the branch commands (`GitArgSchema`, no refspec, no `refs/…`, not `HEAD`), and the lock reason goes as `--reason=<text>`, one line. Paths from git (`C:/x` on Windows) are given back in the platform's form. Worktree commands emit `git.changed` with reason `worktrees` (and `branches`, since which branches are checked out where changed). The hidden `git.worktree.reveal` opens a worktree's folder in the file manager, for the UI only, and only a listed worktree that is a folder on disk (the host opens the path with the system's default handler).

The smoke section [`parts/git/worktrees.ts`](../../../../src/main/smoke/parts/git/worktrees.ts) builds a repository in a temporary folder, its worktrees beside it in the same folder, and checks: status and list in the main worktree; add with a new branch at the default folder and with an existing branch at a relative folder with a space; the list and `worktreePath`; checkout and delete of a branch in another worktree refused naming its folder; add refusing a folder inside a worktree, one that is not empty, a branch in use, `branch` with `newBranch`, and option-like and refspec input; lock with a reason, remove refusing it while locked, unlock, and the main worktree not lockable; remove refusing the main worktree, a folder that is no worktree, and a dirty worktree until `force`; then, in the linked worktree opened as a workspace, its status and `worktree.linked`, the list marking it current, remove refusing it there and from the main workspace while it is open, stage, a file in the index and commit (the main worktree seeing the branch move), blame giving the lines to the commit made there, a pull request draft of its branch against the shared `main`, a stash shared with the main worktree and popped, a merge stopped on a conflict showing as its own operation and not the main worktree's, with `git.conflict.get` reading its stages and labels (from the linked worktree's own `MERGE_MSG`) and `git.conflict.resolve` writing and staging its file while the main worktree's stays as it was, and the watcher seeing its index and commit, refs moved from the main worktree, and a worktree added and locked in a terminal; prune of a worktree whose folder was deleted; reveal; agents listing while add, remove, lock, unlock and prune are gated and change nothing, and reveal refused to them; the main worktree opened through a junction (and on Windows with a lower-case drive letter) not taken for a linked one; and, once the last linked worktree is removed and git deletes `worktrees/`, the watcher seeing the next worktree added and locked in a terminal.

## Pull requests

Pull requests of the workspace's GitHub repository, through the GitHub CLI ([`pr.ts`](pr.ts), commands in [`commands-pr.ts`](commands-pr.ts)). gh runs signed in as you, with your own `gh auth login`, so Quiver never sees or stores a GitHub token. Every call is its own gh process run in the repository root with stdin closed (or holding a body), prompts, update notices, colour and the pager off (`GH_PROMPT_DISABLED`, `GH_NO_UPDATE_NOTIFIER`, `CLICOLOR_FORCE=0`, `GH_PAGER=cat`, `GIT_TERMINAL_PROMPT=0`), and asks for `--json`, which `packages/core/src/gh-parse.ts` reads. gh is found on PATH, then in `C:\Program Files\GitHub CLI` on Windows; `QUIVER_GH_PATH` overrides it with a path or a quoted command line, which is how the smoke points it at its fake. On Windows `gh.exe` (or `.com`) is looked for in every PATH folder before anything else, since a `gh.cmd` wrapper in an earlier folder would otherwise win and then fail to start: batch files are never run, as that would take a shell, and when only one is found the error names it and says to point `QUIVER_GH_PATH` at the `gh.exe` it starts. Nothing is stored.

The repository is picked from the configured remotes the way gh picks it (the one `gh repo set-default` marked, then `upstream`, `github`, `origin`, then the first) and handed to every call as `--repo host/owner/name`, so gh never guesses and no input can point it at another repository. The host is always named, github.com included: without it gh takes `GH_HOST`, or the only host it is signed in to, and would read and write a same-named repository on GitHub Enterprise. Remotes on github.com count, plus a GitHub Enterprise host gh is signed in to (or `GH_HOST`). When none does, the error names the remotes with their URLs, minus any user and password in them (`https://oauth2:<token>@…` shows as `https://…`).

| Command | What it gives or does |
| --- | --- |
| `git.pr.status` | `{ installed, authenticated, user, repo, message }`: whether gh is installed, signed in (the active account) and the workspace is a GitHub repository, with what to do next when something is missing (`repo` is `owner/name`, with the host in front on GitHub Enterprise). Never fails for a missing piece, nor when gh cannot be started or times out: that comes back as `authenticated: false` with gh's problem as the message. |
| `git.pr.list` | Pull requests, newest first: `filter` mine (`--author @me`), review-requested (`review-requested:@me`) or all; `state` open, closed, merged or all; `limit` up to 100. Each has its review decision, labels and a roll-up of the head commit's checks (`failure` when any failed, else `pending` when any runs, else `success`; cancelled and timed-out count as failed, as GitHub counts them). |
| `git.pr.get` | One pull request with its body, line counts, files, reviews and comments. |
| `git.pr.checks` | The checks on the head commit (gh's exit codes 1 and 8 for failed and pending checks are read as such, not as errors). `failedLogs` adds, for up to 5 failed Actions jobs, the last 60 lines of `gh run view --job <id> --log-failed` without timestamps or colours, under `## <step>` headings, or `logError` saying why there is none. Each log is read up to 4 MB; past that gh is stopped and `logError` says the log is too large, rather than giving lines from its middle. |
| `git.pr.diff` | The pull request's changes as `git.diff` gives them, read from `gh pr diff`: status, line counts and patch per file, a patch over 512 KB left out and marked `truncated`. gh's output is read up to 32 MB; past that the files read so far come back, the last one marked `truncated`. |
| `git.pr.open` | `gh pr view --web`: the page opens in your browser (also when an agent calls it; it only reaches pull request pages of the picked repository). |
| `git.pr.checkout` | `gh pr checkout`: fetches the branch and switches to it; gives back the new `git.status`. A pull request from a fork (`isCrossRepository` in `gh pr view`) is refused with `INVALID_INPUT` and `details.reason: 'fork'` unless `allowFork: true`: its branch is someone else's code, `.quiver/` included, and its MCP servers, mock servers and realtime connections marked to start with the workspace would run their commands on the next open. |
| `git.pr.create` | A pull request from the current branch, which must be pushed where `git push` sends it: to `branch.<name>.pushRemote` (or `remote.pushDefault`) under its own name when one is set, else to its upstream (`branch.<name>.remote`, a configured remote, and `branch.<name>.merge`). An upstream of another name counts only with `push.default=upstream`; otherwise a branch made with `git checkout -b hotfix origin/release` counts as not pushed, as does one that would push to the base itself (with no `base` given and no `origin/HEAD`, the default branch comes from `gh repo view`). A head on a fork goes as `owner:branch`; a head whose remote is not on the repository's GitHub host (an upstream on GitLab) is refused, since gh would take a same-named branch on GitHub. A branch with commits its remote-tracking branch does not have is refused until they are pushed, since gh opens the pull request from what is on the remote. `base`, `draft`, `labels` (no commas or double quotes, which gh would split on). The title and labels are passed as `--flag=value` and the body on stdin, so none of them can be read as an option. |
| `git.pr.comment` | Adds a comment to the conversation; the body goes on stdin. Gives back the comment's address. |
| `git.pr.draft` | A title, description and labels for a pull request from the current branch, made from git alone ([`draft.ts`](draft.ts), [`commands-draft.ts`](commands-draft.ts)); see below. |

### Drafting a pull request

There is no language model in Quiver: `git.pr.draft` (`{ base?, includePatch? }`) builds a draft from git data, and an agent connected over MCP can write prose on top of it. It reads only, works before the branch is pushed and without gh.

- **Base**: `base` when given, refused with `INVALID_INPUT` (`details.reason: 'bad-base'`) unless `git rev-parse --verify <base>^{commit}` finds a commit, so a range or a missing branch never reaches the diff (and `GitArgSchema` refuses an option-like one). Otherwise the default branch of the remote gh would pick (the one `gh repo set-default` marked, then `upstream`, `github`, `origin`, then the rest): its recorded `HEAD`, else its `main` or `master`, else a local `main` or `master`; with none of them `INVALID_INPUT` (`'no-base'`). `baseRef` is the ref compared with (`origin/main`), `base` the name a pull request takes (`main`).
- **Commits and files**: against `git merge-base <base> HEAD`, so commits the base gained since do not show. `commits` are oldest first, merges (of the base into the branch, mostly) left out of the list and the count, at most the newest 250 listed while `stats.commits` counts them all (the body notes the earlier ones left out). `files` are `git diff --raw --numstat -z <merge base> HEAD` with status and +/−.
- **Title**: the single commit's subject; otherwise the branch name made readable (`feat/git-blame` → "Git blame"), or the first subject on a detached HEAD.
- **Body**: the repository's pull request template, looked up in `.github/pull_request_template.md`, `.github/PULL_REQUEST_TEMPLATE.md`, `docs/`, the root, then the first file (by name) of `.github/PULL_REQUEST_TEMPLATE/`; a template over 64 KB, a link, or a file reached through a linked folder that leads out of the repository is skipped. The first heading for what changed (What changed, Summary, Changes, Description and the like, whatever the case, emoji or punctuation) gets the commit subjects with their bodies indented under them (trailers such as `Co-Authored-By` dropped), and the first Files heading the files grouped by top folder with each group's +/−; what the template had there (a hint in a comment) stays above the list, and every other section and the line endings are kept. Headings inside code fences and HTML comments do not count. Without a template the body has Summary (the commits) and Changes (the files). `template` and `templatePath` give back what was used.
- **Labels**: from the branch prefix (`feat`/`feature` → `enhancement`, `fix`/`bugfix`/`hotfix` → `bug`, `docs` → `documentation`, also under a namespace such as `me/fix/…`), kept only when `gh label list` of the picked repository has them, in its spelling. Without gh, signed out, off GitHub or with gh failing, the labels are empty and the draft is still made.
- **Patch**: with `includePatch`, the `base...HEAD` diff in `patch.text`, cut at the last line end within 200 KB, with `patch.truncated`.

The pure parts (template sections, title, labels, grouping, the cut) are in `packages/core/src/pr-draft.ts`.

When gh is not installed the commands fail with `NOT_FOUND` and `details.reason: 'no-gh'`; when it is signed out with `AUTH_REQUIRED` and `details.reason: 'gh-signed-out'`; in a repository with no GitHub remote with `NOT_FOUND` and `details.reason: 'not-github'` (and `not-a-repo` outside a repository, as the local commands); any other gh failure is `REQUEST_FAILED` with gh's own message.

Polling is driven by the views, so nothing runs while none is open: while the pull requests are on screen they call the hidden `git.pr.refresh` every 60 seconds (`force` for a refresh button). The host then asks gh for a fingerprint of the open pull requests (number, last update and check states, since a finished check run does not change `updatedAt`), at most every 30 seconds per workspace however many views ask, and emits `git.changed` with reason `prs` when it differs from the last one; every view reloads on that event. Create and comment emit it straight away; checkout emits `status` and `branches`.

Agents may call `git.pr.status`, `git.pr.list`, `git.pr.get`, `git.pr.checks`, `git.pr.diff`, `git.pr.open` and `git.pr.draft`. `git.pr.checkout`, `git.pr.create` and `git.pr.comment` are mutating: they get what the agent permissions say (refused in the default read-only mode, asked about in ask mode). `git.pr.refresh` is plumbing and not listed. A checkout made by an agent runs with `GCM_INTERACTIVE=never`, as the local fetch, pull and push do, and a fork's pull request needs `allowFork` from an agent too.

The smoke section [`parts/git/pr.ts`](../../../../src/main/smoke/parts/git/pr.ts) runs against [`fake-gh.ts`](../../../../src/main/smoke/fake-gh.ts), a Node script that answers from a state file, exits like gh and refuses any repository but its own (named with its host); the section writes it to a temporary folder and removes it, and restores `QUIVER_GH_PATH`, in its `after` hook. It checks the status and errors with gh missing, not startable, a batch-file gh (on Windows), signed out and in a repository whose only remote is not on GitHub (with a token in its URL that never shows), the list with its filters and roll-up, a pull request's detail and a missing one, checks of a failing (with the failed log's excerpt, and a non-Actions check's `logError`), a pending and a checkless pull request, the diff, open, the refresh announcing a finished check run once and honouring its limit, create refusing an unpushed branch, an option-like label, a label with a comma, a branch whose upstream is the base, one tracking a branch of another name, one that would push to the default branch gh names, and one whose upstream is on GitLab, and then creating from a fork branch with the title and body kept literal and from a push remote, comment, a fork's checkout refused and then allowed with `allowFork`, checkout switching the branch with its events, every call carrying `--repo github.com/owner/name` and running in the repository root, and agents reading lists and checks while create, comment and checkout are gated and never reach gh.

The smoke section [`parts/git/draft.ts`](../../../../src/main/smoke/parts/git/draft.ts) builds a repository with a bare clone as `origin` (its `HEAD` set to `main`) and a github.com remote, and drafts a branch of two commits that was never pushed: without gh against `origin/main`, with the readable branch title, the commits oldest first and the files; the default body with bodies indented, trailers dropped and files grouped by folder; labels from the branch prefix in the repository's spelling when the fake gh lists them, and none (the draft still whole) when `gh label list` fails; the repository's template filled under What changed with its hint and other sections kept, then the first file of `.github/PULL_REQUEST_TEMPLATE/` with its Files section; a given base as a branch and as a remote-tracking branch, and a missing ref, a range and an option-like base refused; an `upstream` remote's `main` taken as the default base before `origin/HEAD`; a detached HEAD named by its short hash; a template behind a `.github` linked out of the repository not read; the patch whole, and cut at a line end within 200 KB with `truncated`; a single commit's subject as the title; a merge of `main` into the branch left out of the commits and files; and agents calling it ungated. With `--shots` it opens the new pull request form on that branch, which fills title, template body, base and label with the commits and files summary, and checks that Draft from changes asks before replacing a typed title and keeps it on Cancel, and that drafting again still compares with `origin/main` rather than the `main` the form filled in (screenshots `32pd` and `32pe`).

## The panel

The renderer half lives in [`ui/`](ui): the sidebar, the tabs below, a status bar item and the palette entries, all over the commands above.

**Sidebar** ([`git-sidebar.ts`](ui/git-sidebar.ts)). The top bar shows the current branch (or the detached commit) with ahead/behind against its upstream, and Fetch, Pull and Push; a branch with no upstream gets Publish instead of Push (`git.push` with `setUpstream`). Clicking the branch name opens the switch dialog. Below it the commit box: a message, Amend, and Commit (`Ctrl+Enter`), enabled once something is staged and a message is written; ticking Amend with an empty box fills in the last commit's message, and amending a commit that is already on the upstream (nothing ahead) asks first, since the branch can then only be pushed with force. When a push is rejected because the remote branch moved on (after an amend or a rebase), the panel offers a force push with lease (`forceWithLease`), which overwrites it only if nobody pushed since the last fetch. The changed files follow in groups, merge conflicts, staged, changes and untracked, each with stage or unstage per file and for the whole group (a conflict's stage marks it resolved). Clicking a file opens its diff: staged files against HEAD, the others against the index; a conflicted file opens in the Conflicts tab instead. Unstaging a staged rename unstages its old path too. A right-click on a file offers Open changes and Blame (the working tree's file, or HEAD's for a deleted one; not for an untracked file, which git cannot blame). The Changes group and Untracked have a Discard button per file and for the group (`git.discard`), behind a confirmation: working changes go back to the index (what is staged stays) and untracked files are deleted. While a merge, rebase, cherry-pick or revert is in progress, a banner under the branch bar says so and how many files are still in conflict, with Continue (enabled once none is), Skip commit for a rebase, and Abort, which asks first; a skip asks too. Then the Stashes (`git.stash.list`): Stash changes asks for an optional message and whether untracked files go too; each stash shows its message and age, opens its changes in a diff tab on a click, and has Apply, Pop and Drop (which asks first), also on a right-click. A merge, rebase, cherry-pick or apply that stops on conflicts says so in a toast and brings the Git sidebar up. Then the local branches (click to switch, right-click for the branch menu below, + for a new one, and a button for the Branches tab) and links to Branches and tags, History and Pull requests. A folder that is not a repository, or a machine without git, gets an empty state with git's message.

The host watches HEAD, the index and refs but not working files, so the sidebar reads `git.status` again on `git.changed`, when the window gets focus, on its refresh button, and every 5 seconds while it is open, the window visible and the folder a repository. The same sidebar serves every workspace with Git open, so a status is kept with the workspace it was read for: after a switch it shows the new workspace's once read, never the previous one's, and the commit box starts empty. Fetch, pull and push spin their button while they run and report in a toast.

**Worktrees** ([`worktrees-section.ts`](ui/worktrees-section.ts), [`worktree-dialog.ts`](ui/worktree-dialog.ts), [`worktree-actions.ts`](ui/worktree-actions.ts)): a sidebar section under the branches listing `git.worktree.list`, each row with its branch (or the detached commit), its folder (shortened when it sits beside the main worktree, `quiver.worktrees/feat-x`) and current, main, locked and prunable badges. A click, or the row's open button, opens the worktree as a workspace of its own (`workspace.open`), on the Git panel the first time; the row's menu also reveals it in the file manager, copies its path, locks it (asking for an optional reason) or unlocks it, prunes, and removes it, which asks first and, when git refuses a worktree with changes, asks again before removing it with force. **New worktree…** (also in the palette) opens a dialog: a new branch from a ref (the current branch by default) or an existing branch no worktree has, and the folder, filled in from the default as the branch is typed and editable. **Prune** is enabled while a worktree's folder is gone. The section reloads on `git.changed` with reason `worktrees` or `branches`.

**Status bar** ([`git-status-item.ts`](ui/git-status-item.ts), the shell's `statusItems`): the current branch, or the detached commit, with ↑ ahead and ↓ behind its upstream when they are not zero, and the merge, rebase, cherry-pick or revert in progress; its tooltip names the upstream. In a linked worktree the branch icon becomes a worktree marker, and the tooltip names the main worktree. A click opens the Git sidebar. It reads `git.status` with `files: false` (the branch alone, without looking for untracked files) of the workspace on screen and again on `git.changed` (the host's watcher sees commits, checkouts and fetches), shows only the result read for the workspace on screen (`invokeResource`'s `current`), and nothing outside a repository or without git. Without git, the host looks for it again at most every 10 seconds, since the lookup walks PATH synchronously.

**Diff tab** (`git.diff`, [`diff-tab.ts`](ui/diff-tab.ts), [`diff-view.ts`](ui/diff-view.ts)): working or staged changes of one file (or all), a commit ("Open in a tab" in the history), two refs compared (the branch menu's Compare: `git diff HEAD <ref>`), or a stash. Several files get a list on the left; the history and a pull request's Files show the same view in place. Side by side, a file is shown whole in the shared CodeMirror merge view (`q-diff-editor`), unchanged stretches folded and highlighted by its extension: the old side is read with `git.file.show` (the index for a working diff, HEAD for a staged one, the parent for a commit, the ref compared from, the stash's base), and the new side is worked out from it and the patch (`applyPatch` in [`git-format.ts`](ui/git-format.ts)), which gives up rather than guess when a context or deleted line does not match. When the old side cannot be had (over 2 MB, binary) or the patch does not fit, and always inline and for a pull request's files, whose base is not local, the hunks are drawn from the unified diff (`parsePatch` and `splitRows`) with old and new line numbers; past 2000 rows they stop until "Show more". The layout picked is shared by every diff on screen. Binary and oversized files say so. A stash tab whose stash was dropped, or moved down by a newer one, says so rather than show another stash. An untracked file has no diff, so its tab says that and offers Stage. Working and staged diffs follow `git.changed` and window focus while their tab is on screen, and catch up once when a hidden one is shown. The host leaves unmerged records out of the diff summary (`--diff-filter=u`) and splits the patch on `diff --cc` too, so a conflicted file is listed once with its own combined patch; its diff is not drawn, and an "Open conflict editor" button takes its place. The file's header has a Blame button, also on a right-click in the file list: a working or staged diff blames the working tree's file, a commit's diff the file at that commit, a comparison at the ref compared to, and a deleted file at the old side; a stash's and a pull request's files have none.

**Conflicts tab** (`git.conflict`, one per path, [`conflict-tab.ts`](ui/conflict-tab.ts)), from a row under Merge conflicts in the sidebar or the button in a conflicted file's diff: `git.conflict.get` of the file, with its kind and what current (ours) and incoming (theirs) are in the header. **Blame current** and **Blame incoming** in the header open the file's Blame tab at the commit that side comes from (`commits`: HEAD, and the commit merged, picked or replayed), to see who wrote the lines on each side; a side without the file, or with no commit of its own (a revert's incoming side, a stash apply), has none. A text file opens in an editable CodeMirror (`q-conflict-editor` in `packages/ui`) where each conflict's current lines are in the accent colour and incoming ones in the warning colour, a diff3 base muted, the marker lines naming their side, and a bar above each conflict: Accept current, Accept incoming, Accept both, Both, incoming first, and Accept base when the conflict has one. Accepting is an ordinary edit (undone with Ctrl+Z) and the file can be edited freely. Above it a counter (Conflict 1 of 2) with previous and next, Take current and Take incoming for the whole file (`take`; asks first when the text was edited here), and Mark resolved, enabled once no conflict and no leftover start, base or end marker line is left (the counter names the line), which writes the text (CRLF again for a file that had it, and without the final line break git added when neither side had one) and stages it. Markers are as long as the file's `conflict-marker-size`. A rebase says that current is the branch being rebased onto. A file one side deleted, or only one side has, explains which and offers Keep the file or Delete the file, with the kept side shown read-only; a binary file, one over 2 MB or one missing on disk offers only Take current and Take incoming. Once resolved, the tab names the files still in conflict, each opening its own tab, or, with none left, offers Continue (the banner's action) and the sidebar. It reads the file again on `git.changed` (`status`) and window focus while on screen. Edits made here are kept through those reads and mark the tab unsaved, so closing it asks first; when the file changed on disk meanwhile, a note says so with Use the file on disk, which drops the edits.

**History tab** (`git.history`): `git.log` of HEAD in pages of 100 with "Load older commits"; picking a commit shows its message, author, date, hash (click to copy) and its files and diff (`git.show`), whose Blame (the header button, or a right-click in the file list) blames a file at that commit. It reloads when HEAD or a ref moves. A right-click on a commit offers check out (detached), new branch here, tag here (a lightweight tag), cherry-pick onto the current branch, revert, reset the current branch here soft, mixed or hard (hard asks first) and copy the hash.

**Blame tab** (`git.blame`, [`blame-tab.ts`](ui/blame-tab.ts)), one per path and ref: `git.blame` of the file, read-only in the shared CodeMirror editor (searchable with `Ctrl+F`, highlighted by its extension) with a gutter left of the line numbers (`lineMarkers` on `q-code-editor`, [`line-markers.ts`](../../../ui/src/code-editor/line-markers.ts) in `packages/ui`). Each run of lines from one commit shows its short hash, author and age once, with a line above it, and a bar coloured by age, faint for the file's oldest commit and strong for its newest (`blameMarkers` in [`git-format.ts`](ui/git-format.ts)); lines not committed yet say so, in the warning colour. Hovering a marker shows the summary, the author with their email and the full date. A click opens the commit in a diff tab on the file's path there, as the history's "Open in a tab" does (a line not committed yet opens the working changes); a right-click offers Open commit, Blame before this commit (its `previous` commit and path, so a rename is followed; disabled for the commit that added the file) and Copy hash. Blaming before a commit, or another ref typed in the ref field (Enter; empty for the working tree), shows it in the same tab, and Back returns to the one before. Ignore whitespace runs `git blame -w`. Files over 2 MB, binary files and a file gone from the working tree show the host's message. A working tree blame reloads on `git.changed` `status` and on window focus, any blame on `branches` (a branch blamed by name moves), while its tab is on screen or once it is shown. It opens from the sidebar's file menu, the Blame button of a diff, the history and the palette.

**Branches tab** (`git.branches`, [`branches-tab.ts`](ui/branches-tab.ts)), from the sidebar or the palette: the local branches with their upstream, ahead/behind, last commit and the current, merged and gone badges, then the remote branches and the tags, under one filter on names and last commit subjects. Each row has a menu (its ⋯ button or a right-click), the same as the sidebar's branch menu: switch (a double-click too), new branch from here, rename, merge into the current branch and rebase the current branch onto it (each asks first), compare with the current branch, set or unset the upstream, delete (asks first, then asks again before deleting with force when git says it is not merged), delete the upstream on the remote (asks, naming the remote) and copy the name. A branch checked out in another worktree has an "in worktree" badge (its folder in the tooltip; a click opens it) and Open worktree in its menu, and every local branch has New worktree from branch (asks for the folder, the default filled in). Switching to a branch another worktree has, from either list or the palette, offers to open that worktree as a workspace instead; Clean up leaves such branches out, since git would refuse to delete them. A remote branch checks out as a local tracking branch and can be deleted on its remote; a tag checks out detached, merges, compares, pushes to a remote (the only one after asking, else the one picked) and is deleted. Clean up lists the merged and gone local branches with checkboxes, merged ones ticked: deleting asks once, and the ones git finds not merged (a gone branch whose pull request was squashed) are named in a second question before they go with force.

**Pull requests tab** (`git.prs`): `git.pr.status` first; when gh is missing, signed out or the repository has no GitHub remote, an empty state says which, with its message (and `gh auth login` to copy when signed out). Otherwise the list on All, Mine or Review requested and Open, Merged, Closed or all states: number, author, branches, labels, draft, the review decision and a check badge (`✓ 3`, `✗ 1/4`, `● 2/2`). New pull request opens a form in the same tab (title, description, base, labels, draft) that says first when the branch is not pushed or has unpushed commits, with a Push or Publish button, and opens the new pull request's tab once created. The form drafts itself with `git.pr.draft` when it opens: on a branch with commits the base lacks, the empty fields get the draft's title, description, base and labels (a field still holding what the form filled in counts as empty); otherwise the title and description start from the branch's last commit. **Draft from changes** fills all four again, against the base typed in Into if any (not the one the form filled in), asking first when that replaces a title, description or labels you wrote; on a branch with no commits against the base it says so and changes nothing. A summary above the fields names the number of commits and files with +/−, the ref compared with, the template used and the first five commits. Labels are comma-separated and passed to `git.pr.create`.

**Pull request tab** (`git.pr`): title, state, branches, line counts, review decision, checks and labels, with Refresh, Add todo, Open in browser (`git.pr.open`) and Check out. Add todo makes a todo of the pull request (`todo.add`, titled `#<number> <title>` with its address as the notes), and none while an open todo has that address in its notes, also inside a markdown link or at the end of a sentence (`/pull/12` is not `/pull/1`). Conversation shows the description, then reviews and comments in time order, and a comment box (`git.pr.comment`). Checks lists every check with its state, workflow, duration and a link to its page (https only, opened in the system browser); failed logs are read only on "Show failed logs" (`failedLogs: true`), since each costs a gh call per failed job. Files shows `git.pr.diff` in the diff view. Checks and Files are read when first opened and kept, not read again on every switch. Checking out a pull request from a fork asks first, explaining that its `.quiver/` folder comes with it, and then passes `allowFork`.

While a pull request tab or the list is the tab on screen, it calls `git.pr.refresh` when it appears and every 60 seconds (only while the window is visible), and reloads on `git.changed` with reason `prs` (a hidden pull request tab once it is shown again); the list's Refresh forces one. Cancel or creating a pull request takes the tab back to the list, also in its saved data, and a filter from the palette shows the list.

**Palette**: Switch branch (local and remote branches, or any ref typed: typed text filters, and the branch picked in the list wins when it is among the matches; a remote branch checks out as a local tracking branch), New branch, Commit staged changes (asks for the message; refused while conflicts are unresolved), Branches, Stash changes, Merge branch into current and Rebase onto (picking the branch is the confirmation), Continue, Skip and Abort of the operation in progress (with the banner's questions, in place of the raw host commands), Delete branch, Git history, Open pull requests, Pull requests waiting on my review, New pull request, Blame file (asks for a path relative to the repository root, and blames the working tree's file) and New worktree.

Not offered: initialising a repository, an interactive rebase, and editing a commit message mid-rebase.

## Agents

Allowed: `git.status`, `git.branch.list`, `git.log`, `git.diff`, `git.show`, `git.fetch` (it moves only remote-tracking refs), `git.stash.list`, `git.stash.show`, `git.tag.list`, `git.file.show`, `git.blame`, `git.conflict.get`, `git.worktree.list`, `git.pr.status`, `git.pr.list`, `git.pr.get`, `git.pr.checks`, `git.pr.diff`, `git.pr.open` (it opens a page of the picked repository in the browser) and `git.pr.draft` (it writes nothing; gh is only asked for the repository's labels).

Gated as mutating, so they follow the agent permissions (refused in the default read-only mode, asked about in ask mode): `git.checkout`, `git.branch.create`, `git.stage`, `git.unstage`, `git.commit`, `git.pull`, `git.push`, `git.branch.delete`, `git.branch.deleteRemote`, `git.branch.rename`, `git.branch.setUpstream`, `git.merge`, `git.rebase`, `git.operation.continue`, `git.operation.skip`, `git.operation.abort`, `git.cherryPick`, `git.revert`, `git.reset`, `git.stash.push`, `git.stash.apply`, `git.stash.drop`, `git.discard`, `git.tag.create`, `git.tag.delete`, `git.tag.push`, `git.conflict.resolve` (it writes the file and the index), `git.worktree.add`, `git.worktree.remove`, `git.worktree.lock`, `git.worktree.unlock`, `git.worktree.prune`, `git.pr.checkout`, `git.pr.create` and `git.pr.comment`.

`git.pr.refresh` and `git.worktree.reveal` are plumbing for the views and not listed for agents. Fetch, pull, push, checkout, remote branch deletion, tag push and the remote HEAD lookup made by an agent run with `GCM_INTERACTIVE=never`, so no sign-in window opens that the agent cannot see, and a fork's pull request needs `allowFork` from an agent too.
