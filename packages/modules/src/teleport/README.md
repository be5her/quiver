# Teleport

Several clusters at once, each a tsh profile with its own status, expiry countdown, browser SSO login and logout. Databases from `tsh db ls` with one-click `tsh proxy db --tunnel` tunnels that become Quiver connections, Kubernetes clusters with a query view that never changes your terminal's kubectl context (read-only queries, a separate set of typed write actions that always ask first, port forwards, and protected clusters), a per-machine history with favourites, and pinned resources from any cluster at the top.

## How it drives tsh

Quiver finds `tsh` from the path in Settings, then PATH, then the copy bundled with Teleport Connect, and spawns it with tokenized arguments and no shell. A cluster is a tsh profile identified by its proxy address: the ones listed in Settings plus every profile tsh already has on disk. One `tsh status --format=json` per minute reports all of them, and every other command carries `--proxy=<addr>`, so several clusters work side by side and your terminal's current profile only changes when you log in. Login runs `tsh login --proxy=<addr>` with no `--auth` flag and no stdin, so the cluster's default SSO connector opens the browser; the process output is shown in the sidebar. Pins are Quiver-side favourites (cluster, kind, name) kept in global config. Tunnels are app-wide: one `tsh proxy db --tunnel` per cluster, database and database user, shared by every workspace, kept alive while a connection uses it and for 30 seconds after. A connection with Teleport access remembers its cluster, starts its tunnel on first use, and a query that fails because that cluster's certificate expired comes back as `TELEPORT_LOGIN_REQUIRED` naming the cluster, with a "Log in again" button.

Teleport settings (cluster proxy addresses, pins, protected Kubernetes clusters, optional tsh path, log in on launch, whether agents may act on protected clusters) live in the global config, never in `.quiver/`; the sessions themselves are the standard tsh profiles in `~/.tsh`, shared with the tsh and kubectl in your terminal.

## Kubernetes

Kubernetes clusters open a query view. There is no command line anywhere, for you or for agents: you pick one operation from a fixed catalogue (`packages/core/src/models/kube.ts`: list, get, describe, logs and followed logs, events, top, rollout status and history, namespaces, API resources, version, `auth can-i`) and fill in its typed fields, and the host turns that into a kubectl argv from a hard-coded template per operation. Resource types come from an enum that leaves out secrets; names, namespaces and containers must be DNS-1123; label selectors match a strict `key=value`, `key!=value`, `key in (a,b)` pattern; tail is a bounded integer, since a `30s`/`15m`/`2h` duration, output one of wide, yaml or json; no value may start with `-`, each value is its own argv element, and every flag name comes from the template. Unknown operations and unknown fields are rejected, and a unit test walks every template to prove none can produce a write verb.

Queries run with `tsh kubectl`, which embeds kubectl, so kubectl does not need to be installed. Each Kubernetes cluster gets a private kubeconfig in the app data folder (`teleport-kube/`), written once per app run by `tsh kube login` with `KUBECONFIG` pointing at it; every query runs `tsh kubectl <template arguments> --kubeconfig=<that file> --context=<its context>` (the flags go after the subcommand, since tsh parses its own flags up to the first positional argument) with no extra environment, so the kubeconfig and current context your terminal uses are never read or changed. The view shows the kubectl part of the command as a one-line, non-editable preview; its tooltip and Copy give the exact command line that will be spawned, tsh path and every flag included, and after a run a collapsible "Command" row shows exactly what ran (`teleport_kube_preview` returns the same line, plus the one-time `tsh kube login` still pending, and every result carries the exact argv). It fills namespace, pod and container pickers from the same catalogue, and shows output with search, copy, exit code and duration; one-shot queries time out after 60 seconds and can be cancelled, and followed logs stream into a 5000-line buffer until stopped. Stop, a timeout, closing the tab and quitting Quiver end every process tsh started for the run, not only the one Quiver spawned: `tsh kubectl` runs kubectl in a second tsh process that shares the output (Quiver uses `taskkill /T` on Windows and a process group elsewhere).

Every run is recorded per machine as its cluster, operation or action and parameters (never a command string), with time, exit code, duration and who ran it, capped at 200 entries plus favourites; entries fill the form back in, rerun, pin or delete, and the file is validated like a live call when it is read, so editing it cannot inject arguments. Actions are marked as actions in the list, and running one again goes through the confirmation again. "Set as kubectl context for my terminal" is a separate button that runs `tsh kube login` against your own kubeconfig, for when you do want your terminal's kubectl switched. The cluster your terminal points at is marked "terminal" in its cluster's list and ticked in Pinned; both come from `tsh status`, which Quiver refreshes after every login and `tsh kube login`, so the mark follows a switch made in Quiver, in your terminal or by an agent, even while that cluster's section is collapsed.

### Actions

Writes are a second, separate catalogue (`packages/core/src/models/kube-actions.ts`) with its own builder, so the read catalogue and its test that no read template can write stay as they were. The actions are scale (deployments, statefulsets, replicasets; 0 to 1000 replicas), rollout restart and undo (deployments, statefulsets, daemonsets; undo optionally to a revision), rollout pause and resume (deployments), delete (one pod or one job by name, optionally with a grace period), cordon and uncordon (a node), set image (one container of a deployment, statefulset or daemonset, to an image that matches a strict `[registry[:port]/]path[:tag][@digest]` pattern) and trigger a CronJob (`kubectl create job <job> --from=cronjob/<name>`, the job name defaulting to `<cronjob>-manual-<time>`). Each one changes exactly one named object in an explicit namespace: the namespace is required, there are no selectors and no `--all`, values follow the same rules as queries (DNS-1123 names, nothing starting with `-`, every value its own argv element, every flag from the template), and a unit test walks every action to prove its argv is exactly the expected kubectl verb and nothing else. `exec`, `apply`, `edit`, `patch`, `drain` and anything that takes YAML, a patch or a command are left out on purpose: each of them can do anything the cluster allows, which no typed form can make reviewable, so they stay in your terminal.

Actions sit in their own group of the operation picker, and the form turns amber when one is picked. Run never runs an action directly: it asks the host for a fresh preview and opens a confirmation that shows the exact command line that will be spawned (tsh path, kubeconfig and context included). Destructive actions (delete, scale to 0, rollout undo, cordon) also ask for the object's name typed, and on a protected cluster the cluster's name; Run stays disabled until what was typed matches. The result shows like a query result. A CronJob trigger's job name is fixed by the preview and the confirmed action is the one that runs, so the preview is exactly what ran.

### Port forwards

The Port forwards panel, above the history, starts `tsh kubectl port-forward <kind>/<name> <local>:<remote> --address 127.0.0.1` to a pod, service or deployment, on a free local port unless you pick one (1024 and up), and lists each forward with its local port while it runs; a forward to the same target and port is reused, also when two identical starts arrive at once. Forwards are app-wide like database tunnels: they keep running when the tab closes, and are stopped as a process tree on Stop, on logout of their cluster, on removing the cluster and when Quiver quits. One whose process ends on its own (the pod went away) stays listed with its last output until you remove it.

### Protected clusters

Right-click a Kubernetes cluster in the sidebar to mark it Protected; the row and the query view get a shield. Every action on a protected cluster asks for the cluster name typed in the confirmation, and the host checks it (`teleport_kube_action` needs `confirmCluster`, `--confirm-cluster` on the [command line](../../../../docs/cli.md)), so only a call that carries the typed name gets through. Agents are refused actions, action reruns and port forwards there outright, even when the agent permissions allow them (mode allow, an allow rule or an approval), unless you tick "Let agents run Kubernetes actions and port forwards on protected clusters" in Settings > Teleport. Under permission mode ask that refusal comes first, so you are never asked to approve a call that would be refused anyway. Actions, their previews and port forwards only go to a cluster that `tsh kube ls` lists under exactly the name given (a fresh listing is tried once), since `tsh kube login` also accepts other names for a cluster, such as an auto-discovered cluster's short name, which would otherwise reach a protected cluster without matching its entry. An agent may protect a cluster but never unprotect one; unprotecting asks first. The list lives in the global config, and survives removing and adding the Teleport cluster again.

## Agents

`teleport_status`, `teleport_db_list`, `teleport_kube_list`, `teleport_db_connect` (start a tunnel, attach a connection), `teleport_pin` and `teleport_cluster_add` are always allowed; `teleport_login`, `teleport_logout`, `teleport_kube_login` (rewrites your kubeconfig), `teleport_db_disconnect` and `teleport_cluster_remove` are gated because they change state your terminal shares or delete pins. Kubernetes: `teleport_kube_query` (the read-only catalogue, its operations and fields spelled out in the tool schema), `teleport_kube_preview`, `teleport_kube_action_preview` (the exact argv of an action, whether it is destructive and whether the cluster is protected), `teleport_kube_stream_read`, `teleport_kube_cancel`, `teleport_kube_portForward_list`, `teleport_kube_history_list` and `teleport_kube_history_pin` are allowed; `teleport_kube_history_rerun` is allowed for a query and gated for an action. `teleport_kube_action` (the action catalogue, spelled out in the tool schema), `teleport_kube_portForward_start`, `teleport_kube_portForward_stop`, `teleport_kube_history_delete` and `teleport_kube_history_clear` are gated, and `teleport_kube_protect` is gated when it unprotects (which agents are refused anyway). On a protected cluster, actions, action reruns and port forwards are refused to agents even when the agent permissions allow them, unless Settings allow them. There is no raw kubectl access for anyone, whatever the agent permissions say: no tool takes a command, arguments or flags.

## Verified by

The smoke runs against a fake `tsh` script that answers status, login, db and kube listing, opens real local tunnels and answers `tsh kubectl` from canned cluster data, logging every argv it receives, so the checks can prove which flags were passed and that nothing else was. It answers the action verbs only in the shapes the action catalogue produces (and refuses every other write), and its `port-forward` opens a real listener that greets each connection with its target. The action checks run every action and compare the argv the fake received with the template and with the preview, reject actions outside the catalogue before kubectl runs, gate actions, action reruns and port forwards for agents (and keep a query rerun allowed), require the typed cluster name on a protected cluster, refuse agents there even in permission mode allow until the Settings switch is on, raise an approval for an agent's action under mode ask and run it once allowed, refuse an agent's action, action rerun and port forward on a protected cluster under mode ask without raising one, refuse a cluster name that is not listed exactly, prove no read query sent a write verb, and start a port forward, connect to it over TCP, reuse it (also for two identical starts at once) and stop it with its process tree gone. The UI checks pick an action from its own group, confirm a scale to 0 by typing the deployment's name, protect the cluster from its context menu and confirm an action with the cluster's name, unprotect it, and start and stop a port forward from the panel. The UI checks also switch the terminal's kube context from a kube row and from the host while the cluster is collapsed, and expect the Pinned tick and the "terminal" mark to move with it.

The smoke checks are in [`src/main/smoke/parts/teleport.ts`](../../../../src/main/smoke/parts/teleport.ts); `npm run smoke -- teleport` runs them alone, with `--shots` for the UI checks.
