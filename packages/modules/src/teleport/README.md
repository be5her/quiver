# Teleport

Several clusters at once, each a tsh profile with its own status, expiry countdown, browser SSO login and logout. Databases from `tsh db ls` with one-click `tsh proxy db --tunnel` tunnels that become Quiver connections, Kubernetes clusters with a read-only query view that never changes your terminal's kubectl context, a per-machine query history with favourites, and pinned resources from any cluster at the top.

## How it drives tsh

Quiver finds `tsh` from the path in Settings, then PATH, then the copy bundled with Teleport Connect, and spawns it with tokenized arguments and no shell. A cluster is a tsh profile identified by its proxy address: the ones listed in Settings plus every profile tsh already has on disk. One `tsh status --format=json` per minute reports all of them, and every other command carries `--proxy=<addr>`, so several clusters work side by side and your terminal's current profile only changes when you log in. Login runs `tsh login --proxy=<addr>` with no `--auth` flag and no stdin, so the cluster's default SSO connector opens the browser; the process output is shown in the sidebar. Pins are Quiver-side favourites (cluster, kind, name) kept in global config. Tunnels are app-wide: one `tsh proxy db --tunnel` per cluster, database and database user, shared by every workspace, kept alive while a connection uses it and for 30 seconds after. A connection with Teleport access remembers its cluster, starts its tunnel on first use, and a query that fails because that cluster's certificate expired comes back as `TELEPORT_LOGIN_REQUIRED` naming the cluster, with a "Log in again" button.

Teleport settings (cluster proxy addresses, pins, optional tsh path, log in on launch) live in the global config, never in `.quiver/`; the sessions themselves are the standard tsh profiles in `~/.tsh`, shared with the tsh and kubectl in your terminal.

## Kubernetes

Kubernetes clusters open a read-only query view. There is no command line anywhere, for you or for agents: you pick one operation from a fixed catalogue (`packages/core/src/models/kube.ts`: list, get, describe, logs and followed logs, events, top, rollout status and history, namespaces, API resources, version, `auth can-i`) and fill in its typed fields, and the host turns that into a kubectl argv from a hard-coded template per operation. Resource types come from an enum that leaves out secrets; names, namespaces and containers must be DNS-1123; label selectors match a strict `key=value`, `key!=value`, `key in (a,b)` pattern; tail is a bounded integer, since a `30s`/`15m`/`2h` duration, output one of wide, yaml or json; no value may start with `-`, each value is its own argv element, and every flag name comes from the template. Unknown operations and unknown fields are rejected, and a unit test walks every template to prove none can produce a write verb.

Queries run with `tsh kubectl`, which embeds kubectl, so kubectl does not need to be installed. Each Kubernetes cluster gets a private kubeconfig in the app data folder (`teleport-kube/`), written once per app run by `tsh kube login` with `KUBECONFIG` pointing at it; every query runs `tsh kubectl <template arguments> --kubeconfig=<that file> --context=<its context>` (the flags go after the subcommand, since tsh parses its own flags up to the first positional argument) with no extra environment, so the kubeconfig and current context your terminal uses are never read or changed. The view shows the kubectl part of the command as a one-line, non-editable preview; its tooltip and Copy give the exact command line that will be spawned, tsh path and every flag included, and after a run a collapsible "Command" row shows exactly what ran (`teleport_kube_preview` returns the same line, plus the one-time `tsh kube login` still pending, and every result carries the exact argv). It fills namespace, pod and container pickers from the same catalogue, and shows output with search, copy, exit code and duration; one-shot queries time out after 60 seconds and can be cancelled, and followed logs stream into a 5000-line buffer until stopped. Stop, a timeout, closing the tab and quitting Quiver end every process tsh started for the run, not only the one Quiver spawned: `tsh kubectl` runs kubectl in a second tsh process that shares the output (Quiver uses `taskkill /T` on Windows and a process group elsewhere).

Every run is recorded per machine as its cluster, operation and parameters (never a command string), with time, exit code and duration, capped at 200 entries plus favourites; entries fill the form back in, rerun, pin or delete, and the file is validated like a live query when it is read, so editing it cannot inject arguments. "Set as kubectl context for my terminal" is a separate button that runs `tsh kube login` against your own kubeconfig, for when you do want your terminal's kubectl switched. The cluster your terminal points at is marked "terminal" in its cluster's list and ticked in Pinned; both come from `tsh status`, which Quiver refreshes after every login and `tsh kube login`, so the mark follows a switch made in Quiver, in your terminal or by an agent, even while that cluster's section is collapsed.

## Agents

`teleport_status`, `teleport_db_list`, `teleport_kube_list`, `teleport_db_connect` (start a tunnel, attach a connection), `teleport_pin` and `teleport_cluster_add` are always allowed; `teleport_login`, `teleport_logout`, `teleport_kube_login` (rewrites your kubeconfig), `teleport_db_disconnect` and `teleport_cluster_remove` are gated because they change state your terminal shares or delete pins. Kubernetes: `teleport_kube_query` (the read-only catalogue, its operations and fields spelled out in the tool schema), `teleport_kube_preview`, `teleport_kube_stream_read`, `teleport_kube_cancel`, `teleport_kube_history_list`, `teleport_kube_history_rerun` and `teleport_kube_history_pin` are allowed; `teleport_kube_history_delete` and `teleport_kube_history_clear` are gated. There is no raw kubectl access for anyone, with or without mutations enabled: no tool takes a command, arguments or flags.

## Verified by

The smoke runs against a fake `tsh` script that answers status, login, db and kube listing, opens real local tunnels and answers `tsh kubectl` from canned cluster data, logging every argv it receives, so the checks can prove which flags were passed and that nothing else was. The UI checks also switch the terminal's kube context from a kube row and from the host while the cluster is collapsed, and expect the Pinned tick and the "terminal" mark to move with it.
