# Teleport

Several clusters at once, each a tsh profile with its own status, expiry countdown, browser SSO login and logout. Databases from `tsh db ls` with one-click `tsh proxy db --tunnel` tunnels that become Quiver connections, Kubernetes clusters with a query view that never changes your terminal's kubectl context (read-only queries, a separate set of typed write actions that always ask first, port forwards, and protected clusters), a per-machine history with favourites, and pinned resources from any cluster at the top.

## How it drives tsh

Quiver finds `tsh` from the path in Settings, then PATH, then the copy bundled with Teleport Connect, and spawns it with tokenized arguments and no shell. A cluster is a tsh profile identified by its proxy address: the ones listed in Settings plus every profile tsh already has on disk. One `tsh status --format=json` per minute reports all of them, and every other command carries `--proxy=<addr>`, so several clusters work side by side and your terminal's current profile only changes when you log in. Login runs `tsh login --proxy=<addr>` with no `--auth` flag and no stdin, so the cluster's default SSO connector opens the browser; the process output is shown in the sidebar. Pins are Quiver-side favourites (cluster, kind, name) kept in global config. Tunnels are app-wide: one `tsh proxy db --tunnel` per cluster, database and database user, shared by every workspace, kept alive while a connection uses it and for 30 seconds after. A connection with Teleport access remembers its cluster, starts its tunnel on first use, and a query that fails because that cluster's certificate expired comes back as `TELEPORT_LOGIN_REQUIRED` naming the cluster, with a "Log in again" button.

Teleport settings (cluster proxy addresses, pins, protected Kubernetes clusters, optional tsh path, log in on launch, Keep me logged in per cluster, whether agents may act on protected clusters) live in the global config, never in `.quiver/`; the sessions themselves are the standard tsh profiles in `~/.tsh`, shared with the tsh and kubectl in your terminal.

### Staying logged in

A certificate lasts the cluster's TTL; the sidebar counts it down, the cluster turns amber with less than 30 minutes left and red once it has expired, and from then on tunnels and Kubernetes queries fail with `TELEPORT_LOGIN_REQUIRED`. **Keep me logged in**, a switch per cluster in the cluster's menu (the `⋯` on its header, or right-click it) and beside the cluster in Settings > Teleport, renews it before that happens. "Log in on launch" is the startup half of it: it logs in once at launch to every cluster whose certificate expired while Quiver was closed.

After every status read (once a minute, and whenever something asks for a fresh one) the session picks the cluster to renew (`proxiesToAutoRenew` in `packages/core/src/models/teleport.ts`): Keep me logged in on, the certificate expiring or expired (a logged-out cluster has nothing to renew), no login running, no attempt on that cluster in the last 10 minutes, and not a certificate whose renewal you cancelled. It runs `tsh login --proxy=<addr>` for it exactly as the sidebar's Log in does, one cluster at a time. While the certificate is still valid Teleport may reissue it without the browser. An expired one needs SSO, so that attempt waits until a Quiver window is in front (the window tells the host when it gains or loses focus through the hidden `teleport.window.focus`, which refuses every caller but the window, so an agent cannot fake it), and is announced with a toast before the browser opens; when tsh opens the browser for an attempt that started in the background (it prints the link line a real `tsh login` prints), Quiver shows a toast and a system notification. A window minimised for an hour therefore renews when it comes back, before your next query. The login output shows in the sidebar as for any login, and a status bar item says "Teleport: renewing" while one runs or waits.

A failed attempt (the browser was closed, SSO failed, tsh kept the old certificate) is shown under the cluster with tsh's reason and retried on the first eligible poll, 10 minutes later. Cancel stops it and holds until that certificate is replaced: the cancel is remembered with the certificate's expiry, so a certificate issued later (by a manual login, here or in your terminal) gets its own attempt. The cluster's header shows a renew mark, and its section says "renews automatically", then "renewed 2 minutes ago", "renewal failed: …, retrying in 8 minutes" or "renewal cancelled; log in to renew this certificate". Turning the setting off, removing the cluster or logging out of it while its renewal runs cancels that `tsh login` and forgets the attempt (it is not a cancel of the certificate), no renewal starts while a logout runs, and a renewal still running when Quiver quits is cancelled without restarting anything. All of this is per app run: the attempts are not written anywhere.

After a renewal everything that holds the old certificate is refreshed: the cluster's database tunnels are restarted (`TunnelManager.restartCluster`: a new `tsh proxy db --tunnel` on the same port when it is still free, with the same users, so connections reconnect through it as after a manual re-login), the private kubeconfig is written again by `tsh kube login` on the next Kubernetes query, and port forwards keep running, except that one which exits within a minute of the renewal (tsh's forwards hold the old certificate too) is started again, once, on the same local port. `teleport.changed` is emitted, so the countdown and state update at once.

## Kubernetes

Kubernetes clusters open a query view. There is no command line anywhere, for you or for agents: you pick one operation from a fixed catalogue (`packages/core/src/models/kube.ts`: list, get, describe, logs and followed logs, events, top, rollout status and history, namespaces, API resources, version, `auth can-i`) and fill in its typed fields, and the host turns that into a kubectl argv from a hard-coded template per operation. Resource types come from an enum that leaves out secrets; names, namespaces and containers must be DNS-1123; label selectors match a strict `key=value`, `key!=value`, `key in (a,b)` pattern; tail is a bounded integer, since a `30s`/`15m`/`2h` duration, output one of wide, yaml or json; no value may start with `-`, each value is its own argv element, and every flag name comes from the template. Unknown operations and unknown fields are rejected, and a unit test walks every template to prove none can produce a write verb.

Queries run with `tsh kubectl`, which embeds kubectl, so kubectl does not need to be installed. Each Kubernetes cluster gets a private kubeconfig in the app data folder (`teleport-kube/`), written once per app run by `tsh kube login` with `KUBECONFIG` pointing at it; every query runs `tsh kubectl <template arguments> --kubeconfig=<that file> --context=<its context>` (the flags go after the subcommand, since tsh parses its own flags up to the first positional argument) with no extra environment, so the kubeconfig and current context your terminal uses are never read or changed. The view shows the kubectl part of the command as a one-line, non-editable preview; its tooltip and Copy give the exact command line that will be spawned, tsh path and every flag included, and after a run a collapsible "Command" row shows exactly what ran (`teleport_kube_preview` returns the same line, plus the one-time `tsh kube login` still pending, and every result carries the exact argv). It fills namespace, pod and container pickers from the same catalogue, and shows output with search, copy, exit code and duration; one-shot queries time out after 60 seconds and can be cancelled, and followed logs stream into a 5000-line buffer until stopped. Stop, a timeout, closing the tab and quitting Quiver end every process tsh started for the run, not only the one Quiver spawned: `tsh kubectl` runs kubectl in a second tsh process that shares the output (Quiver uses `taskkill /T` on Windows and a process group elsewhere).

Every run is recorded per machine as its cluster, operation or action and parameters (never a command string), with time, exit code, duration and who ran it, capped at 200 entries plus favourites; entries fill the form back in, rerun, pin or delete, and the file is validated like a live call when it is read, so editing it cannot inject arguments. Actions are marked as actions in the list, and running one again goes through the confirmation again. Only you rerun actions: an agent's rerun of an action is refused before anything is asked, since the agent permissions would decide it by the rerun command instead of `teleport_kube_action` and its approval would show only an entry id; the agent runs the entry's action (which `teleport_kube_history_list` returns) with `teleport_kube_action` instead. "Set as kubectl context for my terminal" is a separate button that runs `tsh kube login` against your own kubeconfig, for when you do want your terminal's kubectl switched. The cluster your terminal points at is marked "terminal" in its cluster's list and ticked in Pinned; both come from `tsh status`, which Quiver refreshes after every login and `tsh kube login`, so the mark follows a switch made in Quiver, in your terminal or by an agent, even while that cluster's section is collapsed.

### Actions

Writes are a second, separate catalogue (`packages/core/src/models/kube-actions.ts`) with its own builder, so the read catalogue and its test that no read template can write stay as they were. The actions are scale (deployments, statefulsets, replicasets; 0 to 1000 replicas), rollout restart and undo (deployments, statefulsets, daemonsets; undo optionally to a revision), rollout pause and resume (deployments), delete (one pod or one job by name, optionally with a grace period), cordon and uncordon (a node), set image (one container of a deployment, statefulset or daemonset, to an image that matches a strict `[registry[:port]/]path[:tag][@digest]` pattern) and trigger a CronJob (`kubectl create job <job> --from=cronjob/<name>`, the job name defaulting to `<cronjob>-manual-<time>`). Each one changes exactly one named object in an explicit namespace: the namespace is required, there are no selectors and no `--all`, values follow the same rules as queries (DNS-1123 names, nothing starting with `-`, every value its own argv element, every flag from the template), and a unit test walks every action to prove its argv is exactly the expected kubectl verb and nothing else. `exec`, `apply`, `edit`, `patch`, `drain` and anything that takes YAML, a patch or a command are left out on purpose: each of them can do anything the cluster allows, which no typed form can make reviewable, so they stay in your terminal.

Actions sit in their own group of the operation picker, and the form turns amber when one is picked. Run never runs an action directly: it asks the host for a fresh preview and opens a confirmation that shows the exact command line that will be spawned (tsh path, kubeconfig and context included). Destructive actions (delete, scale to 0, rollout undo, cordon) also ask for the object's name typed, and on a protected cluster the cluster's name; Run stays disabled until what was typed matches. The result shows like a query result. A CronJob trigger's job name is fixed by the preview and the confirmed action is the one that runs, so the preview is exactly what ran.

### Port forwards

The Port forwards panel, above the history, starts `tsh kubectl port-forward <kind>/<name> <local>:<remote> --address 127.0.0.1` to a pod, service or deployment, on a free local port unless you pick one (1024 and up), and lists each forward with its local port while it runs; a forward to the same target and port is reused, also when two identical starts arrive at once. Forwards are app-wide like database tunnels: they keep running when the tab closes, and are stopped as a process tree on Stop, on logout of their cluster, on removing the cluster and when Quiver quits (quitting waits up to 8 seconds for them to stop); no forward starts on a cluster while it is being logged out, and a forward that fails to start stays listed until its process is gone. One whose process ends on its own (the pod went away) stays listed with its last output until you remove it.

### Protected clusters

Right-click a Kubernetes cluster in the sidebar to mark it Protected; the row and the query view get a shield. Every action on a protected cluster asks for the cluster name typed in the confirmation, and the host checks it (`teleport_kube_action` needs `confirmCluster`, `--confirm-cluster` on the [command line](../../../../docs/cli.md)), so only a call that carries the typed name gets through. Agents are refused actions and port forwards there outright, even when the agent permissions allow them (mode allow, an allow rule or an approval), unless you tick "Let agents run Kubernetes actions and port forwards on protected clusters" in Settings > Teleport (action reruns are refused to agents on every cluster). Under permission mode ask that refusal comes first, so you are never asked to approve a call that would be refused anyway. This holds for agents talking to Quiver over MCP: the [command line](../../../../docs/cli.md) is you, so an agent that can run a shell as you can still act on a protected cluster with `quiver teleport.kube.action --confirm-cluster <name>`. Actions, their previews and port forwards only go to a cluster that `tsh kube ls` lists under exactly the name given (a fresh listing is tried once), since `tsh kube login` also accepts other names for a cluster, such as an auto-discovered cluster's short name, which would otherwise reach a protected cluster without matching its entry. An agent may protect a cluster, by the exact name `tsh kube ls` lists, but never unprotect one; an agent's unprotect is refused without asking you. At most 200 clusters can be protected. The list lives in the global config, and survives removing and adding the Teleport cluster again.

## Agents

`teleport_status` (with each cluster's `autoRenew` and last `renewal`), `teleport_db_list`, `teleport_kube_list`, `teleport_db_connect` (start a tunnel, attach a connection), `teleport_pin` and `teleport_cluster_add` are always allowed; `teleport_login`, `teleport_logout`, `teleport_kube_login` (rewrites your kubeconfig), `teleport_db_disconnect` and `teleport_cluster_remove` are gated because they change state your terminal shares or delete pins, and `teleport_cluster_autoRenew` (Keep me logged in on or off) is gated because it changes what Quiver does on this machine: logins that may open the browser. Kubernetes: `teleport_kube_query` (the read-only catalogue, its operations and fields spelled out in the tool schema), `teleport_kube_preview`, `teleport_kube_action_preview` (the exact argv of an action, whether it is destructive and whether the cluster is protected), `teleport_kube_stream_read`, `teleport_kube_cancel`, `teleport_kube_portForward_list`, `teleport_kube_history_list` and `teleport_kube_history_pin` are allowed; `teleport_kube_history_rerun` is allowed for a query and refused for an action (agents run the entry's action with `teleport_kube_action`). `teleport_kube_action` (the action catalogue, spelled out in the tool schema), `teleport_kube_portForward_start`, `teleport_kube_portForward_stop`, `teleport_kube_history_delete` and `teleport_kube_history_clear` are gated, and `teleport_kube_protect` is allowed when it protects (the exact listed name only) and refused when it unprotects. On a protected cluster, actions and port forwards are refused to agents even when the agent permissions allow them, unless Settings allow them. There is no raw kubectl access for anyone, whatever the agent permissions say: no tool takes a command, arguments or flags.

## Verified by

The smoke runs against a fake `tsh` script that answers status, login, db and kube listing, opens real local tunnels and answers `tsh kubectl` from canned cluster data, logging every argv it receives, so the checks can prove which flags were passed and that nothing else was. It answers the action verbs only in the shapes the action catalogue produces (and refuses every other write), and its `port-forward` opens a real listener that greets each connection with its target. The action checks run every action and compare the argv the fake received with the template and with the preview, reject actions outside the catalogue before kubectl runs, gate actions and port forwards for agents (and keep a query rerun allowed), refuse an agent's action rerun even in mode allow while the user can still rerun it, let agents protect a cluster by its exact listed name only, require the typed cluster name on a protected cluster, refuse agents there even in permission mode allow until the Settings switch is on, raise an approval for an agent's action under mode ask and run it once allowed, refuse an agent's action, action rerun, unprotect and port forward under mode ask without raising one, refuse a cluster name that is not listed exactly, prove no read query sent a write verb, and start a port forward, connect to it over TCP, reuse it (also for two identical starts at once) and stop it with its process tree gone. The UI checks pick an action from its own group, confirm a scale to 0 by typing the deployment's name, protect the cluster from its context menu and confirm an action with the cluster's name, unprotect it, and start and stop a port forward from the panel. The UI checks also switch the terminal's kube context from a kube row and from the host while the cluster is collapsed, and expect the Pinned tick and the "terminal" mark to move with it.

Keep me logged in runs with the poll shortened to 400 ms (`QUIVER_TELEPORT_POLL_MS`, which the session reads for every poll) and the fake's certificate expiry moved into the expiring window. The fake logs every argv it gets, reissues a still valid certificate without the browser line and prints it for an expired one, and can be told how long a login takes and how long the next certificate lasts. The checks expect no login for an expiring cluster with the setting off; with it on, exactly one `tsh login --proxy=<addr>` within a poll, the cluster back to logged in with a new expiry, its tunnel restarted on the same port with the same users while the other cluster's is untouched, the connection still answering, the next Kubernetes query running `tsh kube login` once more and only once, and a port forward from before the renewal restarted on the same local port when its kubectl dies, but not a second time; turning the setting off mid-attempt cancelling that login and leaving no record; a cancelled renewal not retried for the same certificate; an expired certificate's renewal waiting while the window is in the background and running once it is in front, with the browser link in the login output; `teleport_cluster_autoRenew` gated for agents, `teleport.window.focus` refused to them, and `teleport_status` showing the renewal. The UI checks read "renews automatically" and "renewed … ago" on the renewed cluster, turn the switch on and off from another cluster's menu, and take screenshots in light and dark. The decision itself (expiring and expired picked, the spacing, the cancel rule, one at a time, a running login blocking) has unit tests beside `proxiesToAutoRenew`.

The smoke checks are in [`src/main/smoke/parts/teleport.ts`](../../../../src/main/smoke/parts/teleport.ts); `npm run smoke -- teleport` runs them alone, with `--shots` for the UI checks.
