# MCP inspector

Connect to any MCP server (a command over stdio, Streamable HTTP, or legacy SSE), browse its tools, resources and prompts, call them with arguments prefilled from the schema, and watch every JSON-RPC message in a traffic log with timings and the process's stderr. Imports the servers a project already declares in `.mcp.json`, `.cursor/mcp.json` or `.vscode/mcp.json`, and can point at Quiver's own server to see exactly what agents see.

## How it works

A server is one JSON file under `.quiver/mcp-servers/`: a transport (`stdio` with a command, arguments, environment variables and a working directory; `http` for Streamable HTTP or `sse` for the older HTTP+SSE pair, both with a URL, headers and auth), plus "connect when the workspace opens" and a log size. Strings take `{{variables}}` from the active environment and `${NAME}` or `${NAME:-default}` from Quiver's own environment, the same syntax Claude Code uses in `.mcp.json`, so an imported entry works unchanged. Connecting runs the MCP handshake with the SDK client, announces the project folder as the root, records the server's info, protocol version, capabilities and instructions, and lists its tools, resources and prompts (refreshed again on `list_changed` notifications). Every JSON-RPC message in both directions, every stderr line of a stdio server and every state change lands in a log of 500 entries (configurable, bodies capped at 256 KB) kept in memory and in `.quiver/local`; responses are paired with their requests so each shows its method, round-trip time and whether it failed. `mcp.tool.call` returns the content blocks, structured content and `isError` flag as the server sent them; `mcp.request` sends any method for the rest. The sidebar lists the servers declared in `.mcp.json`, `.cursor/mcp.json` and `.vscode/mcp.json` that are not imported yet, and "This Quiver" adds Quiver's own server bound to the current workspace.

## Call recorder

The other direction: what agents call on Quiver's own MCP server. "Call recorder", at the top of the sidebar and in the command palette, opens a tab with Start, Pause, Resume and End. While a recording runs, every `tools/call` request that reaches the server is listed as it arrives: the time, the agent, the tool, whether it succeeded, how long it took, and on click its arguments and the result the agent got back. Calls that never reach a command are kept too, marked failed: refused mutations, invalid arguments, tools that do not exist. Calls that arrive while paused are not kept. The list filters by text, by agent and to failed calls only, and the status bar shows `REC` with the count for as long as a recording runs, whatever is on screen.

A recording belongs to the app, not to a workspace (each call says which workspace it ran against), and lives in memory only: nothing is written until it is ended and saved with "Save as…", which asks for a place anywhere on disk and writes one JSON file (`format: "quiver.mcp-recording"`, the start and end times, and the calls with their arguments and results). Starting a new recording, discarding one or quitting Quiver drops what was not saved; the first two ask first. A recording ends itself at 5,000 calls or 50 MB, keeping what it has. The file holds arguments and results exactly as the agent sent and received them: results have secrets masked as always, but an argument an agent passed (a password for a new connection, say) is in there in plain text, so treat the file accordingly.

The agent is the client's name and version from the MCP handshake (`claude-code 2.1.0`). The server keeps no sessions, so on `initialize` it hands the client an `Mcp-Session-Id` that carries that name, and clients send it back with every later request; a client that sends none is named after its `User-Agent`.

## Agents

Listing, saving, importing, `mcp_connect`, `mcp_ping`, the tool, resource and prompt listings, `mcp_resource_read`, `mcp_prompt_get` and `mcp_log_list` are allowed; `mcp_tool_call` decides per call and lets tools annotated `readOnlyHint` through while gating every other tool; `mcp_disconnect`, `mcp_server_delete`, `mcp_log_clear` and `mcp_request` are gated. The call recorder is not exposed to agents at all: they cannot start, stop, read, save or drop a recording.

## Verified by

The smoke runs a dependency-free stdio script plus SDK-built Streamable HTTP and legacy SSE endpoints: import from `.mcp.json`, initialize, tools with annotations and structured output, resources and templates, prompts, log notifications, list-changed refresh, a process that exits, and a connection to Quiver's own server. For the call recorder it records agents calling Quiver over HTTP (named by handshake, by session and by User-Agent; successful, refused, invalid and unknown calls), pauses, resumes, ends, saves the file and reads it back, then drives the same from the UI. The inspector's UI is driven too: the tools list with a call and its result, the traffic log, reading a resource and a resource template, rendering a prompt, and the handshake info. Unit tests cover the recorder's states and limits (`packages/core`) and the agent naming over a real HTTP round trip (`packages/mcp`).
