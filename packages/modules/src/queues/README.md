# Queues

Kafka topics, SQS queues and RabbitMQ queues: list them with their counts, peek at messages without consuming them, produce messages, tail a destination live, and see Kafka consumer group lag. Connections are committed under `.quiver/queues/<id>.json`; passwords and keys stay in `host.secrets`. The plan it was built from is in [docs/plans/git-runner-queues.md](../../../../docs/plans/git-runner-queues.md).

## Connections, messages and Kafka

**Connections** are committed one per file under `.quiver/queues/<id>.json` (`queues.connection.save` changes only the fields it is given). Passwords and keys are passed as `secrets` by name (`password` for Kafka SASL and RabbitMQ, `secretAccessKey` for SQS), encrypted with `host.secrets` into `.quiver/local/queues-secrets.json`, and never returned: the commands list only the names of the secrets a connection has. A URL with a user or password in it is refused. `queues.connection.test` tries a saved connection, unsaved settings, or changes on top of a saved one; the last form is mutating, since it sends the saved secrets to whatever the changes point at.

**Commands**, the same for every broker through its `QueueDriver` (`drivers/`); what a broker cannot do answers `NOT_SUPPORTED`:

- `queues.connection.list` / `get` / `test`; `save` / `delete` (mutating; a save that changes anything but the name stops the connection's running tails, since they keep the client they started with; delete stops them, closes its clients and drops its secrets)
- `queues.destination.list` / `describe` (counts, partitions and their offsets, non-default settings); `purge` / `create` / `delete` (mutating)
- `queues.message.peek`: up to `limit` messages, newest (`latest`) or oldest (`earliest`), across partitions or from one, without consuming them
- `queues.message.produce` (mutating): body, key, headers and partition; the broker's id comes back
- `queues.message.wait`: blocks until a new message whose body, key or a header value contains `match`, or the timeout, which starts once the consumer is in place (a Kafka group join takes a few seconds)
- `queues.consumer.start` / `stop` / `read` / `list`: live tails kept in memory (the last 1000 messages each), read with a cursor and an optional `match`; `dropped` says how many left the buffer unread. Starting a tail is not mutating and each holds a consumer on the broker, so at most 20 run per workspace, and one nobody read for 10 minutes is stopped (its messages stay readable). A tail of a destination that does not exist is `NOT_FOUND`, on every broker
- `queues.group.list`: Kafka consumer groups with state, members and lag per partition
- `queues.history.list` / `clear` (clear is mutating): produced messages (bodies cut at 64 KB) and purges, creates and deletes, per machine in `.quiver/local/queues-history.jsonl`

**Events**: `queues.changed` with `reason: 'connections'` when secrets change, a connection is deleted or a destination is created or deleted; `'messages'` after a produce, purge or history clear; `'consumer'` (with `consumerId`, at most four a second) while a tail receives and when it stops. Connection files are announced by the store.

**Memory broker** (`kind: memory`): an in-process broker with topics, partitions and offsets like Kafka, one per connection and workspace. The first message to a topic creates it (a peek or tail of a missing topic does not). It lives until the connection is deleted, the workspace closes or Quiver quits. It backs the smoke and lets the panel be tried without a broker.

Drivers keep their state (the memory broker's topics, Kafka's pooled clients) under an id scoped by workspace, since a connection file is committed and two checkouts of one project opened at once carry the same id: closing one checkout never touches the other's broker. Quitting stops every tail and disconnects every pooled client.

**Kafka** (`kind: kafka`, through `kafkajs`): `brokers` (`host:port`), `clientId`, `ssl`, and `sasl` (`plain`, `scram-sha-256`, `scram-sha-512`) with `username` and the secret `password`. Admin and producer clients are pooled per connection and rebuilt when its settings or password change; closing the workspace disconnects them. Peeks, tails and waits each join a throwaway group (`quiver-peek-…`, `quiver-tail-…`) that commits nothing and is deleted afterwards, so no real group's offsets move; every `quiver-` group is left out of `queues.group.list`. A produce to a topic that does not exist creates it when the broker allows auto-creation. A peek reads the newest or oldest `limit` of every partition from their watermarks and merges them by time; a tail or wait from `latest` starts at the end offsets of the moment it was asked for, not of its group join a few seconds later. Purge deletes records up to the end of every partition. Internal topics (`__…`) are not listed.

The offset arithmetic (`packages/core/src/queues-kafka.ts`) and the tail buffer and matching (`queues-messages.ts`) are unit tested in `packages/core` and exported from `@quiver/core`.

The smoke's `memory` section always runs: connections and secrets on disk, create, produce, peek (newest, oldest, one partition), describe, history, tails from latest and earliest with cursors and filters, a tail of a missing topic not found, the cap of 20 tails, wait and its timeout, purge, deleting a topic and a connection, a rename keeping a connection's tails running and a change of its settings stopping them, two workspaces sharing a connection id keeping brokers of their own, closing the workspace, and the gating of the mutating tools over MCP. Its `kafka` section runs the same flow against a real broker when `QUIVER_SMOKE_KAFKA=host:port` is set (topics get a fresh name and are deleted), and prints a SKIP line otherwise.

## SQS

**Connection** (`kind: sqs`, through `@aws-sdk/client-sqs`): `region`, and either an access key (`accessKeyId`, with the secret `secretAccessKey`, plus the secret `sessionToken` for temporary `ASIA…` keys) or an AWS `profile` from `~/.aws/config` and `~/.aws/credentials` (SSO profiles included). With neither, the SDK's default chain applies (environment variables, the default profile, an instance role); an access key wins over a profile when both are set. `endpoint` points the client somewhere else, such as LocalStack (`http://localhost:4566`); with an endpoint the region defaults to `us-east-1`, and the connection needs an access key of its own (LocalStack takes any, such as `test`/`test`): an endpoint is committed with the connection, so it never gets the profile's or the environment's credentials. For the same reason a stored access key is bound to the endpoint and region it was saved for: when a pulled commit points the connection elsewhere, every call is `AUTH_FAILED` ("re-enter the secret for the new endpoint") before anything is sent. The binding is kept per machine in `.quiver/local/queues-secret-bindings.json`; typing the key again, or changing the endpoint or region in Quiver, binds it anew, while a save that leaves them as they are (a rename) does not. A key stored before bindings existed is bound to where the connection points the first time it is used. The region is taken in lower case, as the SDK puts it in hostnames. One client is pooled per connection and rebuilt when any of these change; a tail still on the old client ends with `CONFLICT` ("The connection changed; start the tail again"), since a destroyed client would go on sending with the old keys to the old host. Deleting the connection, closing the workspace or quitting destroys it.

**Destinations** are queue names. A queue URL is taken too, but only on the connection's own endpoint, SQS's hosts in its region (`https://sqs.<region>.amazonaws.com`) or a host SQS itself answered with in a queue URL; any other host is `INVALID_INPUT` before a request is sent, and the client never follows a queue URL to another host, so a destination cannot send a signed request elsewhere.

**Listings**: `queues.destination.list` has the first 1000 queues (one ListQueues page, each then described; queues past it are reached by name) with the approximate visible count as `messages`, what is in flight or delayed, FIFO, and the dead-letter queue and max receive count. `describe` adds the queue URL and ARN, FIFO settings (content-based deduplication, scope, throughput), the redrive allow policy and the queues that send their failures to this one when it is a DLQ, visibility timeout, retention, delay, receive wait, size limit, encryption and timestamps.

**Peek, and why SQS cannot really peek**: SQS has no read that leaves a message untouched. A peek receives with a visibility timeout of 0, so the message stays visible to every other consumer and is never deleted, but each receive still adds one to its `ApproximateReceiveCount`, and SQS moves a message to the queue's dead-letter queue on the receive that takes the count past the redrive policy's `maxReceiveCount`. A peek therefore receives each message about once: it reads the redrive policy and the visible count first, then receives rounds of up to ten, each long polling a second so SQS looks at every server, until it has enough, a round brings nothing, it has seen as many as the queue held, or three rounds in a row bring nothing new (one on a queue with a redrive policy), within 10 seconds. A round that brings fewer than asked does not end it, since SQS often does that with more waiting. A later round can hand back messages already received, so once any message it has is one receive short of `maxReceiveCount` it makes no further round and answers with what it has: a peek never takes a message it received itself past the limit. Its first round still adds one to every message it gets, so a message that earlier peeks, tails or consumers left at the limit goes to the DLQ on the next peek: with `maxReceiveCount` 5, about five peeks of a quiet queue (fewer past ten messages, where rounds can receive a message twice) send its messages there. It orders what it saw by sent time: `earliest` stops at `limit`, `latest` collects up to 500 and keeps the newest of those. SQS hands out older messages first, so on a standard queue with a long backlog the newest may not be among them. A FIFO queue hands out each group from its oldest message, and at visibility 0 those stay first in line, so past ten messages its newest are never handed out: a `latest` peek of a FIFO queue holding more than ten is refused (`INVALID_INPUT`, before anything is received); peek from `earliest`. In-flight and delayed messages are not seen. Each message comes back with its message attributes as `headers`, its group id as `key`, its FIFO sequence number as `offset`, and system attributes (receive count, first receive, group and deduplication ids, sender) in `attributes`.

**Produce**: headers go as String message attributes. `groupId` (or else `key`) is the message group, which FIFO queues require and standard ones take for fair queueing; `dedupId` is the deduplication id, which a FIFO queue without content-based deduplication requires; `delaySeconds` delays a message on a standard queue (FIFO queues only take a delay for the whole queue). The SQS message id comes back.

**Tails and wait do not consume either.** Kafka tails read with a throwaway group and memory tails only listen, so an SQS tail does the same: it long-polls (20 seconds) with a visibility timeout of 0 and never deletes. It remembers the ids it has handed on (the last 10,000), so each message appears once even though it stays on the queue. But messages nobody consumes come straight back, and every receive counts: while a receive brings only messages already handed on, the tail waits 1, 2, 4, 8, 16, then 20 seconds between receives, so a message left on a quiet queue is received about 7 times in its first minute and 3 times a minute after that, and a new message starts the wait over at a second (an empty queue's long poll waits on its own and counts nothing). The tail reads the queue's redrive policy when it starts and ends with `CONFLICT` once a message it receives is one receive short of `maxReceiveCount`, rather than move it to the DLQ; a tail (or wait) from `latest` refuses to start with `CONFLICT` if its first look finds such a message, and that look stops before the round that could push it over. From `latest`, what is on the queue when the tail starts does not count: what a first look sees, received the way a peek receives (except what was sent while it long polled), and anything sent more than 5 seconds before the tail started that the look missed. On a standard queue holding many messages SQS may keep handing out older ones before new ones show; on a FIFO queue a group holding ten or more messages hands out only its oldest, so new messages in that group reach a tail or a wait only once the queue's consumers take the older ones. Throttling, what the SDK marks retryable, 5xx answers and network errors are retried after 1, 2, 4… up to 30 seconds; anything else would fail the same way again and ends the tail with the reason: a deleted queue, refused or expired credentials (an expired SSO session included), a disabled or missing KMS key (`INVALID_INPUT`, or `AUTH_FAILED` when KMS refuses access), an invalid request or any other 4xx.

**Agents**: since every receive can move a message closer to the DLQ, `queues.message.peek`, `queues.message.wait` and `queues.consumer.start` are mutating on SQS connections: agents get them refused until mutations are allowed, while listings, `describe` and the connection commands stay open to them.

**Admin**: `purge` (SQS allows one per queue a minute; a second within it is `CONFLICT`), `create` (a FIFO queue's name must end in `.fifo`, and such a name makes a FIFO queue; an existing name, asked of SQS rather than the URL cache, is `CONFLICT` rather than SQS's silent reuse) and `delete`. Consumer groups are a Kafka notion, so `queues.group.list` is `NOT_SUPPORTED`. AWS errors map to Quiver codes: a missing queue is `NOT_FOUND`, refused or expired credentials `AUTH_FAILED`, invalid parameters `INVALID_INPUT`.

Shaping attributes, messages and peeks, when a peek stops receiving, the region and queue URL hosts, the key's binding, error codes and which errors a tail retries (`packages/core/src/queues-sqs.ts`) are unit tested in `packages/core`. The smoke's `sqs` section runs against `src/main/smoke/fake-sqs.ts`, a fake of the SQS JSON protocol on 127.0.0.1 that the section starts and closes itself and that redrives to a DLQ past `maxReceiveCount` as SQS does (queues made uneven hand out short, overlapping rounds as SQS's sampling does, and a queue with the KMS key `alias/disabled` refuses receives): the key committed and its secret not, test with a key, a wrong key, a missing secret or region and an AWS profile, an endpoint refused the profile and the default chain, create (standard, FIFO, conflict), describe with a redrive policy and DLQ sources, list with counts, peek newest and oldest with every receive at visibility timeout 0, each message received once per peek and nothing deleted, queue URLs taken for the endpoint and refused for other hosts, SQS's own URLs taken for a region given in mixed case, FIFO groups, deduplication and the refusals including a `latest` peek past ten messages, tails from latest and earliest that hand each message on once and leave it on the queue, wait, a tail that stops one receive short of the DLQ and peeks that push a message into it, peek, wait and tail on uneven queues of 15 messages with `maxReceiveCount` 1 and 2 leaving the DLQ empty, a peek that goes on through short rounds until it has seen all 25 messages of a queue, a tail ended by a disabled KMS key instead of retrying, a tail ended once a hand-edited connection file changes the key its client signs with, purge and its once-a-minute limit, a tail ended by its queue's deletion mid long poll, a pulled endpoint refused the stored key (also after a rename, with nothing sent) until the key is typed again, and over MCP peek, tail, wait and produce refused until mutations are allowed, then a peek allowed.

## RabbitMQ

**Connection** (`kind: rabbit`): `host`, `port` (5672, or 5671 with `ssl` for amqps), `vhost` (`/` by default), `username` and the secret `password`, plus `managementUrl` for the management HTTP API (`http://<host>:15672` when empty, `https://<host>:15671` with `ssl`), reached with the same user (as basic auth, so with `ssl` an `http://` management URL is refused, and redirects are not followed). The driver builds the AMQP options from these fields. The host must be a plain host name (letters, digits, dots, hyphens, underscores), an IPv4 address or an IPv6 one (bare or in brackets); anything else, such as a pasted URL (`amqp://user:pass@host`) or a host with `\`, `?`, `#` or `:` in it that a URL parser would read as another host, is refused when the connection is saved, before anything is committed, and the derived management URL must name that same host. A `managementUrl` must be `http://` or `https://`, with no user, password, query or fragment. amqps verifies the broker's certificate, with no way to turn that off. With neither user nor password set it uses RabbitMQ's `guest`/`guest`, which a broker accepts from localhost only. One AMQP connection and one confirm channel are pooled per connection (scoped by workspace), rebuilt when the settings or the password change, and closed when the connection is deleted, the workspace closes or Quiver quits; peeks, checks and tails each open a channel of their own on it. Every AMQP call after connecting gives up after 15 seconds (a peek after 30) rather than hang on a broker that stopped answering. `test` tries AMQP and the management API apart and says which failed.

**Destinations**: queues by name, exchanges as `exchange:<name>`; `.` and `..` are refused as names, since the management API's URLs would resolve them as path segments. The listing comes from the management API: queues with their message count (ready plus unacknowledged), consumers, type and arguments, then the named exchanges with their type; the default exchange, the built-in `amq.*` ones (they can still be published to) and Quiver's own `quiver-tail-…` queues are left out. Its counts lag a few seconds, as the management API's statistics do; `describe` of a queue takes the ready count and consumers from AMQP, which is exact, and lists its bindings (`describe` of an exchange lists where it routes). Without the management API, listing fails and `describe` of a queue falls back to the AMQP counts.

**Peek** takes up to `limit` messages from the head of the queue with `basic.get` and requeues them all (`nack` with requeue), so nothing is consumed, but **every peeked message is marked redelivered**, and on a quorum queue each peek counts as a delivery toward its `delivery-limit`, after which the broker dead-letters or drops it. That is why a RabbitMQ peek is mutating for agents (see Agents): repeated peeks can move messages to the dead-letter queue. While a peek holds them, other consumers do not get those messages and go on with later ones. `latest` reads up to 1000 from the head and keeps the newest `limit`; RabbitMQ cannot read a queue from its tail. Messages a consumer holds unacknowledged are not seen. The queue's type comes from the management API; when that refuses the user (one without the management tag) or cannot be reached, the peek goes on over AMQP as a classic or quorum queue. A stream queue (`x-queue-type: stream`) is consumed from an offset instead, which marks nothing: `earliest` from its first, `latest` from `limit` before the end by the management API's count, reading on until nothing arrives for 0.75 seconds (or nothing at all for 3). An exchange holds no messages, so peeking or purging one is `NOT_SUPPORTED`. Messages come back with `key` = the routing key, a sequence number as `id`, and the exchange, routing key, redelivered flag and AMQP properties (message id, content type, …) as `attributes`.

**Produce** goes to a queue through the default exchange (a `key` is refused there: the routing key is the queue's name), to an exchange with `exchange` set and `destination` as the routing key, or to `exchange:<name>` with `key` as the routing key. It is published persistent and mandatory on a confirm channel with a fresh `messageId` (the id that comes back) and a timestamp; a missing queue or exchange is `NOT_FOUND`, and a message no queue is bound for is `REQUEST_FAILED` instead of dropped silently. While the broker blocks the connection (a memory or disk alarm), a produce is `REQUEST_FAILED` at once instead of waiting for a confirm that does not come. `partition` and `delaySeconds` are refused.

**Live tails and waits** never consume. They declare an exclusive, auto-deleted queue of their own (`quiver-tail-…`, holding at most 1000 messages and dropping the oldest, so a tail that falls behind never piles up on the broker), start consuming it and bind it with copies of the bindings that route to the destination now: for a queue, each of its bindings; for an exchange of any type, the routing keys and header arguments it is bound with (other tails' bindings left out); a delayed-message exchange counts as its `x-delayed-type`. Only copies, never a catch-all: a binding of its own would make messages routable that no binding routes, taking them from the exchange's alternate exchange and from mandatory publishers' returns. So **messages that no binding routes are not shown by a tail**, and an exchange with no bindings cannot be tailed (`NOT_SUPPORTED`). Bindings added after the tail started are not followed. The tail's queue dead-letters to `quiver-tail-no-dlx`, an exchange that does not exist (its argument overrides a policy's), so what it drops never reaches the broker's real dead-letter queues; it expires after a minute unused, and a tail whose setup fails deletes it. What to bind comes from the management API (bindings and exchange types), so tails need it. Exchanges that send each message to one bound queue only (consistent hash, modulus hash, random and other plugin types) are refused, as is a queue bound to one (`NOT_SUPPORTED`): a tail's queue bound there would take its share of the messages away from the real queues. A tail therefore sees a copy of what exchanges route to the queue, but not messages published straight to the queue by name (the default exchange cannot be copied), so a queue reached only that way cannot be tailed (`NOT_SUPPORTED`; peek it instead). `earliest` on a queue first replays up to 1000 of the messages already in it, the way peek does, so it is mutating for agents like peek (what the tail's queue gets meanwhile is held and shown after the replay; a message routed during the replay may show twice); on an exchange it is the same as `latest`. A stream queue is tailed from its `first` or `next` offset. A tail of a missing queue or exchange is `NOT_FOUND`; one whose channel or connection closes ends with the broker's reason, and one whose queue or exchange is deleted (checked every 5 seconds) ends with "… was deleted", rather than keep its copied bindings.

**Admin**: `create` makes a durable classic queue, or for `exchange:<name>` a durable topic exchange (`CONFLICT` if it exists); `purge` empties a queue; `delete` removes a queue or an exchange. There are no consumer groups.

The naming (with `.` and `..` refused), connection options (plain hosts and IPv6, the vhost escaped for amqplib, which unescapes it), the management URL (no credentials, query or other scheme, no `http://` with ssl, a derived URL naming the host itself), management API rows, tail bindings (copies for every exchange type and never a catch-all, other tails left out, exchanges that pick one queue refused, delayed-message exchanges by their type), stream offsets and message conversion (`packages/core/src/queues-rabbit.ts`) are unit tested in `packages/core`. The smoke's `rabbit` section always runs the management API checks against a fake it starts and stops (`src/main/smoke/fake-rabbit-mgmt.ts`, on 127.0.0.1, no AMQP behind it): `test` telling AMQP and management apart, a pasted URL refused by `test` and by `save` with nothing committed, a host with `\` or `?` in it refused the same way, an `http://` management URL refused with ssl and one with a query refused, both before any request, the listing with counts and without default, `amq.*` or tail entries, the vhost sent as `%2F`, describe of a queue and an exchange, not found, `.` and `..` refused, peek and purge of an exchange, tails of a default-exchange-only queue, of a consistent-hash exchange and of a queue it feeds, and of exchanges with no bindings (one with an alternate exchange and only a leftover tail's binding) refused, a tail of a topic exchange asking for its bindings to copy, a wrong password, a peek going on over AMQP when the management API refuses the user, and over MCP a peek and an `earliest` tail blocked as mutating while a `latest` tail is not. With `QUIVER_SMOKE_RABBIT=amqp://user:pass@host:5672/vhost` (and `QUIVER_SMOKE_RABBIT_MANAGEMENT` when the API is not on port 15672 of that host) it also runs against a real broker: create, produce to a queue and through an exchange, peek oldest and newest without consuming and with the redelivered flag, exact describe, tails of a queue and of an exchange, a publish no binding routes still refused while an exchange tail runs, wait, unroutable and missing targets, a tail ended by its queue's deletion from another client, a stream queue, purge and delete. Everything it makes has a fresh name and is deleted again; it prints a SKIP line otherwise.

## The panel

**Sidebar**: the connections, each with its kind (`MEM`, `KAFKA`, `SQS`, `AMQP`) and name, opening to its topics or queues with their message counts (and `FIFO` on SQS FIFO queues). The counts follow what is produced, purged, created or deleted from Quiver, at most once a second (a listing can cost a call per queue on SQS, and an agent may produce a hundred messages in a row); the row's Refresh asks the broker again for what other clients did. The `+` of the header asks for a name and a broker and opens the new connection's settings; a connection's `+` creates a topic (with its partitions) or a queue (standard or FIFO on SQS); its `…` and right-click menu also test, edit and delete it. A topic or queue's menu opens it on its messages, the producer, the live tail or (Kafka) its consumer groups, and purges or deletes it.

**Connection tab**: the fields of its broker (Kafka brokers, client id, TLS, SASL and user; SQS region, profile or access key id, and an endpoint for LocalStack; RabbitMQ host, port, virtual host, TLS, user and management API; nothing for the memory broker), saved with Ctrl+S; an empty RabbitMQ port goes back to the default. The password or secret access key is a password box, shown where the settings use it (not on the memory broker, nor on Kafka without SASL): what is typed goes to `queues.connection.save` as a secret and is cleared, the stored one is never read back (the box says whether one is stored, and "Remove on save" drops it), and what was typed in a box that is no longer shown is not sent. A secret stored for settings the connection no longer has (another broker's, or a Kafka password with SASL off) is listed by name under the box with its own "Remove on save". Test tries what is on screen: the saved connection, or the unsaved changes on top of it with a newly typed secret. A Kafka connection has a Consumer groups view: every group with its state, members and total lag, opening to committed offset, end and lag per partition.

**Destination tab**: the topic or queue with its counts, partitions and consumers, and Refresh, Purge and Delete. Views:

- **Messages**: a peek (`queues.message.peek`) as a table of position (partition:offset, or the broker's id), key, header count, body and time; newest or oldest first, 10 to 500, and one partition or all on a topic. A message opens beside the table with its key, headers and attributes and the body pretty-printed when it is JSON (rows are reached with Tab and opened with Enter or Space); Produce again copies it into the producer. On Kafka and the memory broker it peeks on open, on every change of its settings and again after each produce or purge of this topic made from Quiver. On SQS and RabbitMQ it peeks only on a click, with the settings of that click, and says why: an SQS peek adds to every message's receive count (a redrive policy can then move it to the dead-letter queue), and a RabbitMQ peek requeues, which marks the messages redelivered.
- **Produce**: key, headers and a JSON or text body (Format pretty-prints it, a warning says when it does not parse), plus the partition on a topic (by key or round robin otherwise), the message group and deduplication ids on an SQS FIFO queue (the group is required) or a delay on a standard one. On RabbitMQ, a queue takes the exchange to publish through (empty for the default exchange; the queue's name is the routing key either way), and an `exchange:<name>` destination takes the routing key instead. Ctrl+Enter sends; the broker's id is shown. "Sent before" reloads a message from this machine's history; one whose body the history cut at 64 KB says so and is not sent again until it is edited. Produce again from a RabbitMQ queue fills in the exchange the message came through rather than its routing key, which a queue would refuse. What is being written stays while another view is on screen.
- **Live tail**: a consumer from new messages or from the start, with Start and Stop and a text filter on body, key and header values that applies to what was already received. It reads as the host announces new messages and once a minute while quiet, so an open tail is not stopped as idle; it keeps running while another view is on screen (a dot on the view says so). Closing the tab stops it and drops it on the host, also when the tab closes while the tail is still starting, or while the tab shows an error instead of the tail (its connection file went away) with the tail held for it. Deleting the topic or queue, from here or by an agent, stops its tails on the host. Switching to another workspace keeps it running and picks it up with what it buffered when you come back; nobody reads it meanwhile, so after 10 minutes away the host stops it as idle (its messages stay readable). A read that fails while the tail may still run is shown under the bar and does not stop it. The SQS tail says that every receive adds to the receive count; the RabbitMQ tail that it reads through a queue of its own and takes nothing, but that from the start it first requeues what is waiting.
- **Consumer groups** (Kafka): the groups reading this topic and their lag on its partitions.

**Confirmations**: purging and deleting a topic or queue, and deleting a connection, ask first; creating a topic or queue asks for its name in a dialog first.

**Palette**: "New queue connection", and "Open topic or queue", which picks the connection and takes a name, listing the matches as it is typed (a name that does not exist yet opens too, so the first message can create it). The dialog opens at once and each connection's names arrive as its broker answers, so a broker that is down holds nothing up.

**Updates**: the views follow `queues.changed` of the workspace on screen only (two checkouts of one project share connection ids), and a destination's peek, counts and producer history only for events about that destination or about none in particular. The connection tab reloads on its file changing and on `reason: 'connections'` for its connection, not on a tail's events.

The smoke's `ui` section (with `--shots`) drives the panel on a memory connection: creating it from the sidebar's dialog and testing it, the Kafka form's fields and password box, a password typed and saved (listed by name, encrypted under `.quiver/local`, absent from the committed file, the box cleared) and then shown as unused and removed after going back to the memory broker, creating a topic with three partitions, starting a live tail, producing a message with a key, a header and a partition, seeing it in the tail (and its filter) and in the peek table with the body pretty-printed, the count in the sidebar, Purge's confirmation (Cancel keeps the message, Purge empties the topic), deleting the topic after its confirmation with its tab's live tail stopped and gone from `queues.consumer.list`, and deleting the connection after its confirmation. ## Agents

Allowed: `queues.connection.list`, `queues.connection.get`, `queues.connection.test` (of a saved connection as it is, or of a draft with secrets of its own), `queues.destination.list`, `queues.destination.describe`, `queues.consumer.stop`, `queues.consumer.read`, `queues.consumer.list`, `queues.group.list` and `queues.history.list`; and, on Kafka and memory connections, `queues.message.peek`, `queues.message.wait` and `queues.consumer.start`.

Gated as mutating, refused until the user enables mutations: `queues.connection.save`, `queues.connection.delete`, `queues.connection.test` with both `id` and `connection` (a draft on top of a saved connection, which would send its secrets to the draft's broker), `queues.destination.purge`, `queues.destination.create`, `queues.destination.delete`, `queues.message.produce` and `queues.history.clear`; and, decided per call from the connection's kind, `queues.message.peek`, `queues.message.wait` and `queues.consumer.start` on SQS, and `queues.message.peek` and `queues.consumer.start` from `earliest` on RabbitMQ.

Reads that change what the broker holds are gated too, decided per call from the connection's kind. On SQS every receive adds to a message's receive count, and past a redrive policy's `maxReceiveCount` SQS moves it to the dead-letter queue, so peeks, waits and tails are mutating there. On RabbitMQ a peek gets and requeues, which marks messages redelivered and counts toward a quorum queue's delivery limit, so peeks and tails from `earliest` (which replay the same way) are mutating; a tail or wait from `latest` binds a queue of its own with copies of existing bindings only (never a catch-all, so it takes nothing from an alternate exchange or a mandatory publisher) and is allowed. Kafka and memory reads stay open.

## Verified by

`npm run smoke -- queues` runs the part, whose sections are in [`src/main/smoke/parts/queues/`](../../../../src/main/smoke/parts/queues), one per driver plus the panel; with `--shots` the UI section runs too. What each covers is described above:

- [`memory.ts`](../../../../src/main/smoke/parts/queues/memory.ts): the commands, secrets, history and agent gating on the memory broker; always runs.
- [`kafka.ts`](../../../../src/main/smoke/parts/queues/kafka.ts): a real Kafka broker, only when `QUIVER_SMOKE_KAFKA=host:port` is set (CI starts no broker).
- [`sqs.ts`](../../../../src/main/smoke/parts/queues/sqs.ts): the SQS driver against the HTTP fake [`fake-sqs.ts`](../../../../src/main/smoke/fake-sqs.ts), redrive included; always runs.
- [`rabbit.ts`](../../../../src/main/smoke/parts/queues/rabbit.ts): the management API parts against [`fake-rabbit-mgmt.ts`](../../../../src/main/smoke/fake-rabbit-mgmt.ts) always, and a real broker only when `QUIVER_SMOKE_RABBIT` is set.
- [`ui.ts`](../../../../src/main/smoke/parts/queues/ui.ts): the panel on a memory connection (screenshots `30a` to `30f`).

Unit tests in `packages/core` cover the drivers' pure parts (`queues-kafka.test.ts`, `queues-sqs.test.ts`, `queues-rabbit.test.ts`, `queues-messages.test.ts`).
