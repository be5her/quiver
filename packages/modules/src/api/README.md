# API client

Collections, requests with params, headers, body and auth, environments with encrypted secrets, checks on responses and collection runs, streamed responses, client certificates and a proxy, a history of what was sent with its responses to compare, imports from curl (bash, cmd.exe and PowerShell copies), OpenAPI, Postman, Insomnia and HAR, export as curl and code, and `{{variables}}` everywhere.

## Variables

Global variables (Settings) apply to every workspace; the active environment of a workspace overrides them; built-in dynamic values (`{{$uuid}}`, `{{$timestamp}}`, `{{$timestampMs}}`, `{{$isoTimestamp}}`, `{{$randomInt}}`) are new on every send. An environment is one committed file under `.quiver/environments/`; values flagged secret are kept encrypted in `.quiver/local/secrets.json` and the committed file carries an empty value.

Variables are highlighted in URLs, params, headers, auth fields and bodies (and in the realtime and MCP inspector fields, which resolve them the same way), unknown ones in red. Hovering one shows its value and whether it comes from the active environment, the global variables or the built-ins, with secrets masked until you click the eye; the pencil edits the value where it is defined (the active environment, secrets staying encrypted, or the global variables). An undefined variable's card offers to define it, in any environment of the workspace (optionally as a secret) or in the global variables; a name that is already a secret in that environment stays secret. Open request and environment tabs, and the global variables in Settings, follow changes made elsewhere (an agent, a git pull or branch switch) unless they have unsaved edits.

## Collections

A collection passes things on to every request inside it, and inside its sub-collections: a base URL, headers and auth, set in its Settings tab (the gear on its row, or Settings… in its menu), with notes beside them. Before variables are resolved, a request is sent as `effectiveRequest` describes:

- **URL.** A request URL starting with `/` gets the nearest non-empty base URL above it in front, its trailing slash dropped, so `{{baseUrl}}/` and `/users` make `{{baseUrl}}/users`. A full URL is left alone.
- **Headers.** The collections' headers go first, from the top level down, and a deeper collection replaces a header of the same name (names compared without case). A request's own enabled header of that name replaces the inherited one; disabled rows pass nothing on.
- **Auth.** A request whose auth is "Inherit from collection" uses the nearest collection that sets one; a collection can inherit from its parent the same way, and at the top level inherit means no auth. New requests created inside a collection inherit; those at the top level start with none.

The request tab shows what it inherits: the inherited headers above its own, each with the collection it comes from (struck through where the request replaces it), the full URL under a relative one with where the base URL comes from, and what "Inherit from collection" resolves to in the Auth segment. Curl export, GraphQL introspection and the masking of what agents see all use the same effective request, and `api_request_get` with `effective: true` returns it, with typed credentials masked for agents. Collections are committed files, so the base URL, headers and auth are shared with the team; keep tokens in a secret environment variable and reference it, as for requests. Collection files written before this read with the defaults (no base URL, no headers, inherit).

## The sidebar

Requests and collections drag onto a collection, or onto the Collections header to go back to the top level; a label by the pointer says where the item will land, and a collection cannot go inside itself or its own sub-collections (`api.collection.move` refuses that too). Only what is under the pointer counts: a drag let go over the item's own collection moves it nowhere. A tab with unsaved edits saves them over the request or collection where it is at that moment, so a move or reorder made meanwhile stays. Items stay sorted by name, so moving things around does not rewrite other files. Right-click a row, or use its … button, for its actions: Open, Rename, Duplicate, Copy as curl, Move to… (a second menu of the top level and every collection) and Delete on a request; New request, New GraphQL request, New sub-collection, Import from curl here, Rename, Move to… and Delete on a collection.

The filter at the top narrows the tree to the requests whose name, method or URL hold every word typed, keeping and opening the collections they are in (without changing which collections are saved as open), and narrows the history the same way, by method, URL, name or status (`404`, `ERR`, `STOP`). Escape clears it. The sidebar shows the last 30 requests sent; Show all (and right-click on an entry, and the palette's "Show request history") opens a Request history tab with up to 500, searchable and filtered by method and by status class, failed or cancelled. A history entry opens as an unsaved draft, or is kept with Save as request: a new request at the top level, with the credentials that were typed into it still masked.

## Sending

Beside Send, a picker switches the workspace's active environment: the same one the sidebar ticks and the status bar shows, so the hover cards and database parameters follow it too. While a request is in flight, Send becomes Stop (Escape does the same); the send ends with `REQUEST_CANCELLED` and its history entry says Cancelled (`STOP` in the sidebar). Agents stop a send by giving `api_request_send` a `sendId` and calling `api_request_cancel` with it.

The Settings segment holds how the request is sent: timeout, whether redirects are followed, whether invalid certificates are accepted, and the cap on the response body kept in memory. It shows the value in effect and saves only what differs from the defaults (30 s, follow, verify, 10 MB) as the request's `options`, so a committed request says "this endpoint needs 120 s" and nothing else. A send uses the defaults, then the request's options, then any `options` the caller passes; introspection uses the request's options too. Copy as curl says what the request does, since curl's defaults differ: `-L` when redirects are followed, `-k` for invalid certificates and `--max-time` when the request sets a timeout.

The Notes segment edits the request's `description`, plain text that agents get from `api_request_get`; its first line is the tooltip of the request in the sidebar. History rows show how long ago they were sent.

## Responses

Redirects are followed by Quiver rather than by fetch, up to 20, so each hop is known. The status line says how many there were, and the Headers view lists every hop (status, method, where it pointed, its time) with its own headers under the final response's. The rules are the browsers': 303 turns anything but HEAD into a GET and 301 or 302 turn a POST into one, dropping the body; 307 and 308 repeat the request as it was; a redirect to another origin (another scheme or port counts, so a downgrade to http does) drops `Authorization`, `Proxy-Authorization`, `Cookie` and every header named like a credential (`X-API-Key`, the header an API key auth sends, `X-Auth-Token`), so a redirect cannot carry a key to a host it was not meant for. With redirects off (Settings), the 3xx is the response.

A thin bar under the status line splits the time into redirects, waiting for the final response and downloading its body; hovering the time or the bar gives the figures. A response that sets cookies gets a Cookies view: name, value, domain, path, expiry (Max-Age wins over Expires) and flags, from the Set-Cookie headers kept one by one (`setCookies`), since the joined header cannot be split where an Expires holds a comma.

The body is searchable (Find, or Ctrl+F in it). A JSON body can be filtered with a JSON path, the subset everyday filtering needs: `$`, `.key`, `['key']`, `[0]`, negative indexes, `[*]` and `.*`, and `..key` at any depth (no filter expressions, slices or unions; a `..` visits each node once, so `$..a..a` stays quick on a deep document, and a path selecting more than 50,000 values is refused); the filter shows what it selects and how many values, or why the path cannot be read, and stays in place across sends. Images are previewed, with Raw for the bytes. PDFs are not previewed: that would need the renderer's content security policy loosened and Electron's plugins enabled, so they, like other binary bodies, are saved instead. Save writes the body as it arrived (not prettified or filtered) to a file chosen in the save dialog, named after the URL and the content type.

## Streamed responses

An event stream (`text/event-stream`) streams on its own, and any other body does when the request's Settings say Stream the response (or the send gives `stream: true`), split into lines: NDJSON and the like. The status and headers show as soon as they arrive; the body becomes a live list of events (name, data, id) or lines with the time each came, following the end until scrolled up, with Stop to close the connection; closing the tab, or sending the request again, closes it too. The host keeps the last 5000 items (or 16 MB of them) of each stream; `api.request.stream.read { streamId, since }` returns those after `since` with `next`, `done`, `dropped` and why it ended, and `api.request.stream.stop` closes it. A line, or an event, that passes 1 MB without ending closes the stream with an error (such a body is not one to stream, and would be kept whole in memory), and when more than 20 streams of a workspace are open at once the oldest is closed, its last read saying so. The timeout covers only the wait for the head. Captures and checks need a whole body, so they do not run on a streamed one, and a collection run reads every body whole. A body that is not streamed but large says how much has arrived while it downloads (`Receiving… 3.2 MB`).

## Checks

The Checks segment holds assertions run on the response after every send: the status, a JSON path into the body, a header, the body text, the time in ms or the size in bytes, compared with equals, does not equal, less than, greater than, contains, matches (a regular expression, tried on the first 64 KB of the text, a miss saying so; a pattern that repeats a group that repeats inside, like `(a+)+`, is refused rather than run, since it could take for ever on a body that does not match), exists or is of type (string, number, boolean, object, array, null). Values compare as numbers or JSON where they are (`$.id` equals `7`, `$.tags` equals `["a"]`), a JSON path selecting several values reads them as an array (so `$.items[*].id` contains `3` works), and `{{variables}}` resolve in the expected value. The response's status line says how many passed (`3/4 checks`) and its Checks view lists each with what it read; the history entry keeps the count. Checks are stored on the request (`checks`, absent when there are none).

## Collection runs

Run collection (the collection's menu, or Run in its Settings tab) sends its requests one after another: its own in their order, then each sub-collection's, by name. Each request's captures are written before the next one is sent, so a login's token reaches the requests after it, and its checks decide the result: passed (a response, every check passing), failed (a check did not pass) or error (no response). The run tab shows every request with its result, HTTP status, time, checks and the failed checks' messages, updated live, with Stop, Run again and "Stop at the first failure"; a row opens its request. Every send is in the history as usual, and a finished run is kept in `.quiver/local/runs.jsonl` with URLs and errors masked like history entries and the send's known secrets scrubbed from what its checks read (a check on a token's JSON path would otherwise keep the token), which is also what `api_run_get` and `api_run_list` hand to agents; the sidebar shows the last run's result (`passed/total`) after the collection's name. The order of requests is set with the up and down buttons in the collection's Settings tab (`order` on each request, written only for collections where it is set); without one, requests go by name.

## Proxy and client certificates

The proxy is the machine's, in Settings under Network: none, the system proxy (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`), or a manual one with a user name and a password kept encrypted, and hosts that bypass it (`localhost`, `.internal.example.com` for a domain and its subdomains, `10.0.0.5:8080`, `*`). Client certificates are the workspace's, on this machine, in the Certificates tab (the shield in the sidebar, or the palette): a host pattern (`api.example.com`, `*.example.com`, optionally with a port) and the files to present, a PEM certificate and key or a PKCS#12 file, with an optional CA to trust for those hosts and a passphrase kept encrypted; they live in `.quiver/local/certificates.json` and are never committed. The most specific pattern wins. Sends, collection runs, GraphQL introspection and realtime connections all go through them, each redirect hop deciding again; undici's proxy tunnels plain http as well as https with CONNECT.

## Cookie jar

Each workspace has a cookie jar, kept on this machine in `.quiver/local/cookies.json`, encrypted with the OS keychain like OAuth tokens and secret variables (session cookies are credentials). Writes go through a per-workspace lock and apply what a send received to the jar as it is on disk, so two sends finishing together keep both their cookies. The cookies a response sets are kept, those of redirect hops too, and sent with every later request they match, as a browser would (RFC 6265): host-only cookies to their host, Domain cookies to its subdomains as well, by path with the longest path first, Secure ones only over https or to a loopback host. A cookie replaces the one with the same name, domain and path; Max-Age=0 or an Expires in the past deletes it; session cookies stay until the jar is cleared. Refused, as a browser would: a Domain the host is not inside; a Domain nobody owns outright, so that one site cannot plant cookies for every other under it (a single label, a public suffix such as `co.uk` or `com.au`, or a hosting platform's shared domain such as `herokuapp.com` or `github.io`, from a short built-in list rather than the whole public suffix list; the host itself is always fine); and a Secure cookie set over plain http, except from a loopback host. A request's own Cookie header wins for the names it sets. A request can turn the jar off in its Settings segment.

The response's Cookies view says what the jar did with each cookie (kept, deleted, refused and why), and the Request view which cookies came from the jar. The jar opens from the cookie button in the sidebar, the palette ("Show cookie jar") or the Cookies view: cookies by domain, to filter, delete one by one or clear. Agents read the jar with `api_cookie_list` (values masked, as the Cookie header already is in what was sent) and add with `api_cookie_set`; deleting and clearing are gated.

## OAuth 2.0

A request or a collection can authenticate with OAuth 2.0: the request carries a token from the token URL as a bearer (or with the header prefix the auth sets). Two grants are offered. Client credentials posts the client's ID and secret, as a Basic header or in the body, with the scopes and an optional audience. Authorization code opens the authorize page in a Quiver window, as the logs module does for Grafana, while a listener on `http://127.0.0.1:<port>/callback` takes the redirect; PKCE (S256) is on unless turned off. The port is a free one unless the auth sets one, for providers that want the exact redirect URI registered; providers that follow the loopback rules for native apps accept any port.

Tokens are kept per machine in `.quiver/local/oauth-tokens.json`, each encrypted with the OS keychain, and shared by every request and collection with the same grant, token URL, client, scopes and audience, so one sign-in serves a whole collection. A token is used until 30 seconds before it expires; then the refresh token gets a new one, and failing that the grant runs again. A send from the UI signs in when it has to. The token request reaches the token URL the way the request itself does: through the proxy, with the client certificate that matches it, and accepting invalid certificates when the request does. The Auth segment has Get token (Get new token when one is cached), Forget token, which also clears the sign-in window's session, and a line saying when the token expires and its scope. The client secret is meant to be a secret variable (`{{clientSecret}}`); typed in, it is masked in the history like other credentials, and the token is masked in what was sent, the history and what agents see. Curl export carries a cached or client credentials token, never opening a sign-in.

Agents get tokens through `api_oauth2_token` (masked), `api_oauth2_status` and `api_oauth2_clear`, and with every send, but never a sign-in: an authorization code token that is not cached and cannot be refreshed is `SIGN_IN_REQUIRED`, to be got once from the Quiver window. Realtime connections and MCP servers do not offer OAuth 2.0.

## Files

A multipart form field can be a file: tick File on its row and choose it, and the value is the file's path. Its file name and content type are sent too, the type guessed from the extension unless the field sets its own. A Binary file body sends one file as the request body, as it is, with a Content-Type from its extension (or the one set beside it; a Content-Type header on the request wins). A file chosen inside the project folder is stored by its path relative to that folder, so the committed request works for everyone; one outside it is stored absolute and works only on this machine, which the body editor says. Files are read while they are sent rather than loaded into memory, with their length sent as Content-Length, and read again when a 307 or 308 redirect repeats the request. What was sent shows a file as `<file name, size bytes>`. A missing file, or a directory, is refused before anything is sent.

## Captures

A request's Capture segment lists values to take from its response after every send and write into the environment, so the next request can use them: a login's token, an id the server made. Each capture names a variable and where to read it: the body by a JSON path (the same subset as the response filter; empty for the whole body, strings as they are and anything else as JSON), a header or a cookie the response set by name, or the status code. They are written to the active environment (or the one the send names) in a single save, through the same path as defining a variable, so a capture marked secret, one whose variable is named like a credential (`token`, `password`, `apiKey`: the names the masking rules know; the Capture segment ticks Secret for them as the name is typed, and the host treats them as secret either way), or a variable that already is secret, is stored encrypted on this machine and the committed file keeps an empty value; what a secret capture read is masked in the response the history keeps and in everything an agent gets back, as the request's own credentials are. The response pane lists what each capture wrote, secret values masked, or why it read nothing; a send without an environment reports every capture as failed and still succeeds. Captures are saved with the request as `capture` (left out when there are none). For agents, `api_request_send` reports `captured` with secret values masked; writing to an environment is what agents may already do with `api_variables_set`, so captures need no extra permission.

## History

Every send is appended to `.quiver/local/history.jsonl`, a plain file on this machine that agents can list, and shows up in the sidebar's History right away, from the UI or an agent. So nothing that is a credential goes into it as it was typed. The request is stored as it was written, with `{{variables}}` still as references (a secret variable is never in there), and with these masked as `••••••••`: the token, password or API key of the Auth tab, the value of `Authorization` (its scheme is kept: `Bearer ••••••••`), `Proxy-Authorization`, `Cookie` and headers or query parameters named like a credential (`X-API-Key`, `access_token`, `password`, `signature` and so on), and a password in the URL. The URL that went on the wire is stored with the same parameters masked, plus every secret the request resolved to, wherever it sits in the URL. Bodies are stored as written.

The request is still sent exactly as typed; only the record of it is masked. Opening an entry from the history gives the request back with the masks in place, so a credential that was typed in has to be typed again, while one that came from a variable just works. A history written before this existed is rewritten, masked, the next time its workspace opens.

Responses of 256 KB or less are kept with their history entry (Set-Cookie values masked, and the secrets the request resolved to, and secret captures read, scrubbed from the headers and the body, a `Location`'s credential parameters masked as a URL's are), unless "Keep responses in the history" is turned off in a request's Settings; that setting is the workspace's, per machine. The history keeps the newest 1000 entries and the responses of the newest 200 of them: when the log is tidied (as the workspace opens, and every fifty sends) older entries lose their response and the oldest go, so the file stays quick to read. A kept response opens with Open response in the history menu. Compare (in the response pane, or Compare… in the history menu) opens two kept responses of a saved request side by side with the changes marked, the newest two by default; Normalise JSON sorts keys and indents both so only real changes show, and Headers adds the status line and headers. `api.history.list` leaves responses out unless `withResponses` is set (`hasResponse` says one is kept), and takes a `requestId`; `api.history.get` returns one entry with its response.

## Code

The Code button copies the request as code that sends it: curl, JavaScript (fetch or axios), Python (requests), Go (net/http), C# (HttpClient) or PowerShell (Invoke-RestMethod), the last one picked first. Show code puts the snippet in the lower pane instead of the response, for the request as it stands (unsaved edits included), with a language to pick (remembered per workspace on this machine) and Copy. The code is what would be sent: variables resolved, the collections' headers, auth and base URL applied, a cached or client credentials OAuth token in place (never a sign-in for a copy), multipart file fields and binary bodies read from their paths, and the request's timeout, redirect and certificate settings where the tool has them. Agents get the same from `api_export_code` with credentials and secret variables masked, as for curl.

## Import

The Import button in the sidebar (and Import here… on a collection, and the palette) reads curl (below) or a file: an OpenAPI document, a Postman collection or environment, an Insomnia export or a HAR recording, JSON or YAML. A file is picked, or its text pasted (Paste a file…, which says what it reads the text as). The whole file is read and converted before anything is saved, so a broken file, or one of another kind, is refused and the workspace stays as it was. An import only adds: a new collection (under the chosen one), its requests and environments; nothing that exists changes. Afterwards the collection opens, and what was found but not imported (scripts, unsupported auth, references to other files) is listed.

- **OpenAPI** 3.0 and 3.1, and Swagger 2.0. The root collection is named after the API, its base URL is the first server (server variables at their defaults; `{{baseUrl}}` when there is none), and each tag is a collection (an untagged operation goes by the first segment of its path). Each operation is a request named by its summary: `{id}` in the path becomes `{{id}}`, query and header parameters are rows with their example (required ones on, optional ones off), and the body comes from the example, or is built from the schema with `$ref`s followed inside the document (eight levels deep and two thousand values at most, so schemas that reference each other many times over stay small). Security schemes become auth with credentials as variables: bearer `{{token}}`, basic `{{username}}`/`{{password}}`, an API key `{{<name>}}`, OAuth 2.0 client credentials or authorization code with `{{clientId}}`/`{{clientSecret}}`; the document's default sits on the root collection and requests that differ carry their own.
- **Postman** Collection v2.1 (and v2.0): folders, requests with raw, URL-encoded, form-data (files by path), GraphQL and file bodies, and bearer, basic, API key and OAuth 2.0 auth on the collection, folders and requests. `{{variables}}` stay as they are and `:name` path segments become `{{name}}`; the collection's variables (and path variables' values) become an environment named after it, secret ones (and those named like a credential) kept secret. A token, password, API key or client secret typed into an auth, and a literal value in a header, query parameter or URL-encoded, multipart or JSON body field named like a credential (`Authorization`, `X-API-Key`, `password`, `client_secret`), becomes a `{{variable}}` whose value is a secret in that environment, so no committed file holds it; the report says which. A credential in an XML or plain text body is not recognised. A Postman environment file imports as an environment. Pre-request and test scripts are listed, not imported.
- **Insomnia** v4 (JSON) and v5 (YAML): the workspace, its folders and requests (gRPC and WebSocket requests listed), `{{ _.name }}` as `{{name}}`, and its environments, each sub-environment with the base environment merged in and nested values as dotted names, values named like a credential kept secret. Credentials typed into an auth, a header, a parameter or a body field become `{{variables}}` with their values secrets in every imported environment (or in one made for them), as for Postman. Template tags (`{% response %}`, `{% faker %}`) are left as they are and listed.
- **HAR** 1.2, as a browser saves it: the API calls (page loads, scripts, styles, images and fonts, and repeated requests, are left out), a collection per host, optionally only one host (`.example.com` for its subdomains too). Cookies and connection headers are dropped, and credentials (`Authorization`, API key headers, token parameters, password and secret fields in bodies) are replaced by `{{variables}}`, so a recording of a signed-in session does not become committed requests carrying its tokens; a send then asks for those variables.

## curl import

Import from curl (sidebar, palette, `api_import_curl`) reads a pasted command with the quoting rules of the shell it was copied for, then maps curl's options to the request the way curl would send it. The shell is detected from the text and can be picked in the dialog (`dialect` for agents):

- **cmd.exe**, Chrome's "Copy as cURL (cmd)": recognised by `^` line continuations or arguments wrapped in `^"…^"`. Read in the two layers Windows applies: cmd.exe's carets (`^x` is a literal `x`, `^` at the end of a line continues it, `^` + line break + empty line is a line break in the value), then the MSVC argument rules (`\"` is a quote, backslashes are only halved in front of a quote). Chrome doubles every backslash in this format, so one that is not in front of a quote reaches curl.exe doubled, and is imported that way.
- **PowerShell**: recognised by backtick line continuations or a command starting with `curl.exe`. `'…'` is literal (`''` for a quote), `"…"` takes backtick escapes.
- **bash/zsh** otherwise, Chrome's "Copy as cURL (bash)" and Postman or Insomnia exports: `'…'`, `"…"`, `$'…'` (ANSI-C escapes), backslash escapes and continuations.

Options are read by their curl meaning, not their position: `--url`, `-X`, `-H`, `-b` (and a `Cookie` header, merged into one), `-u`, `-A`, `-e`, `--oauth2-bearer`, the `-d` family (several are joined with `&` and make it a POST unless `-X` says otherwise; `--data-urlencode` encodes its value; `--json` also sets `Content-Type` and `Accept`; `-d @file`, `--data-binary @file` and `--json @file` make a Binary file body), `-F`/`--form-string` (multipart; `-F name=@file;type=…;filename=…` becomes a file field, `--form-string` keeps an `@` as text), `-G` (the data goes into the query string) and `-I`; `-XPOST`, bundled flags like `-sSL` and `--opt=value` work too. Options that only affect how curl runs (`--compressed`, `-k`, `-L`, `-s`, `-o`, timeouts, TLS and so on) are accepted and ignored. The query string becomes params, each key and value decoded once.

A command that cannot be imported exactly is refused and nothing is saved, with the shell and the line and column in the error: an unterminated quote, a `^`, backtick or `\` left over as an argument, an argument still wrapped in `^…^` (cmd syntax read as bash), something the shell would expand (`$VAR`, `$(…)`) or treat as an operator (an unquoted `&`), standard input (`-d @-`), a body file joined with other data, a field read from a file as text (`-F name=<file`), a header or cookie file, an unknown option, a second URL, or malformed `%`-encoding in the query.

## GraphQL

A GraphQL request is an ordinary request whose body type is `graphql`: a query document, variables as JSON text (with `{{variables}}` inside) and an optional operation name. Over POST it goes out as `{"query","variables","operationName"}` JSON; over GET the same three become query parameters. `api.graphql.introspect` runs the standard introspection query against the request's URL with its headers and auth, and caches the result as SDL under `.quiver/local`, keyed by endpoint; the editor uses it for autocompletion and lint, the Docs tab explores it (search and an SDL view), and `api.graphql.schema` hands it to agents. Documents with several operations get an operation picker; prettify reformats the document.

## Agents

Listing, reading, creating, saving, sending and cancelling requests, listing, reading, creating, saving, renaming and moving collections, the environment commands, `api_oauth2_token` (the token masked; no sign-in for agents, which get `SIGN_IN_REQUIRED` instead), `api_oauth2_status`, `api_oauth2_clear`, `api_cookie_list` (values masked) and `api_cookie_set`, `api_export_code`, collection runs (`api_collection_run`, `api_run_get`, `api_run_list` and `api_run_cancel`: an agent may already send every request, so running them in order is not gated), `api_collection_reorder`, `api_request_stream_read` and `api_request_stream_stop`, `api_history_get`, `api_network_get` (no password) and `api_certificate_list` (file names only, no passphrase), the imports (`api_import_curl`, `api_import_openapi`, `api_import_postman`, `api_import_insomnia` and `api_import_har`, which only add; a file given by `path` must be inside the workspace folder for agents), `api_graphql_introspect`, `api_graphql_schema` and `api_variables_list` (the variables in effect, secrets masked) are allowed. Files a request sends (multipart file fields and binary bodies) must be inside the workspace folder when an agent sends it, links followed; the UI may send any file. A file an agent imports from is checked the same way. Deletes are gated (`api_cookie_delete` and `api_cookie_clear` too), and so are `api_network_save` (the machine's proxy), `api_certificate_save` and `api_certificate_delete` (credentials to present), and `api_response_save`, which writes a file; with mutations enabled it still only writes inside the workspace folder for agents, links followed (a junction inside the project cannot lead the write out of it), and never under `.git` or `.quiver/local`. `api_variables_set` decides per call: changing a value in the active environment is allowed, changing a global variable (which every workspace uses) is gated; `api_variables_define` likewise adds a variable to any environment freely and to the global variables only with mutations enabled. Secret values are masked for agents everywhere: in the environment and variable listings, in the history, and in what a send reports back. `api_request_send` returns the request as it went on the wire (`sent`) with credential headers and parameters masked and every secret the request resolved to masked in the URL, the other headers and the body; the URL of each redirect hop is masked the same way, as is an error that quotes the URL, and so are `api_export_curl` and the endpoint URL of the GraphQL schema commands. The UI gets all of these unmasked. The response itself is the server's, passed on with the same known secrets scrubbed from its headers and body (what a secret capture read among them, and a `Location`'s credential parameters masked), as the history keeps it; so a server that echoes what it receives shows an agent what it was sent, with the credentials masked.
