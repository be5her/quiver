# Core

The engine, with no Electron or UI framework in it: the command registry (`defineCommand`, `defineModule`, the mutating gate), the models every module shares, variable resolution, the file store behind `.quiver/`, the colour palettes, and small pure helpers (arrays, activity bar layout, JSON formatting that keeps numbers as written, relative times). Everything here is unit-tested with vitest (`npm test`); if a piece of logic can be written without I/O, it belongs here with a test beside it.

`src/index.ts` is the pure entry point, safe to import from the renderer. `src/node/` holds the Node-only parts: the workspace manager, the file store, the global config store, the JWT validation behind `tools.jwt.verify`, and the child process helpers (`spawnTree`, `killTree`, `whichSync`, `runToEnd`) the git, gh, runner and teleport code starts programs with: a run can be stopped as a whole tree, times out and caps its output on request, never rejects, and survives a program that exits before reading its input.

## Storage

- `.quiver/<collection>/<id>.json`: committed, one file per item, diffable in pull requests. Quiver watches the folder, so files an agent writes by hand, a `git pull` or a branch switch show up without a restart. An item is read only from the file its id names: a file whose `id` is not its own name (`z.json` saying it is `b`) or not a valid file name is left out with a warning, since saves and deletes of that id act on `<id>.json` and would not stick. A save keeps what a newer Quiver wrote: a module names its committed collections and their item schemas in `defineModule({ collections })`, and the store puts back every field of the stored file that the schema has no key for (`keepUnknownFields` in `src/unknown-fields.ts`), at any depth: objects by key, array items by their `id`, a union only while the same option fits the old and the new value. A known field the save leaves out stays out, nothing that was not in the file is added, and the command returns what it saved, without those fields.
- `.quiver/local/`: gitignored (the store writes the `.gitignore` itself). UI state (tabs, tree state), request and query history, requests captured by mock servers, realtime message logs, MCP traffic logs, the logs and Metabase query histories, env file backups, fetched GraphQL schemas, the todo list, and secrets (environment values, database passwords, Metabase API keys) encrypted with the OS keychain.
- SQLite files referenced by a relative path resolve against the project folder, so a committed connection works for every teammate.
- Global config lives in the Electron user data folder as `config.json`: theme and palette, recent and open workspaces (in the order the title bar shows them), global variables, the MCP port, the agent permission mode, rules and pause switch (`mcp.permissions`, `mcp.paused`; `allowMutating` is kept in step for older builds and migrated on load, and a file where an older build switched it off loads as read-only), each workspace's agent rules by workspace id (`mcp.workspaceRules`: per machine, never in the project, where anyone who can commit could plant an allow), the update channel, the activity bar arrangement (`activityBar`: order and hidden modules), and the Teleport settings (cluster proxy addresses, pins, optional tsh path, log in on launch). Nested sections are merged one level deep and normalised on load, so an older or hand-edited file cannot break the app. The Kubernetes query history and the private kubeconfigs Quiver queries through live in `teleport-kube/` in the same folder, per machine. Grafana sign-ins for the logs module are Electron session partitions (`Partitions/quiver-grafana-<origin>`) in the same folder, one per Grafana address, and so are Metabase sign-ins (`Partitions/quiver-metabase-<origin>`), one per Metabase address. While the MCP server listens, `cli-endpoint.json` and `cli-token` in the same folder tell the `quiver` command line where to connect and with what token (made anew on every start, readable by the user only). A headless `quiver` run keeps its own global config in a `quiver-cli` folder beside it (or `--data-dir`).

## Commands and the mutating gate

A command declares an id, a scope (`global` or `workspace`), a zod input schema and a handler. The schema is validated on every call and becomes the MCP tool schema. `mutating` is a boolean or a function of the input and the call context. For MCP callers the registry asks `decideAgentPermission` (`src/permissions.ts`): the workspace's and the global rules, then the permission mode for a mutating call. It lets the call through, refuses it with `MUTATION_BLOCKED` and a `details.reason`, or asks `host.approvals` and waits for the user. Before asking it runs the command's `beforeApproval`, if it has one: a refusal the handler would make whatever the user answers (a protected Kubernetes cluster) comes back at once, so the user is never asked about a call that is refused anyway (`AgentApprovals` in `src/approvals.ts` keeps what waits, the timeout and what was allowed until restart, and `maskArguments` masks what the dialog shows). `ctx.signal`, which the MCP layer sets from the request, aborts when the agent goes away, and the waiting call is then refused with reason `cancelled`. Handlers see who is calling (`ctx.caller` is `ui`, `mcp`, or `cli` for the [`quiver` command line](../../docs/cli.md), which is the user's own process with the user's rights and unmasked results; only `mcp` is gated), and for `mcp` the agent (`ctx.agent`); they mask secrets for agents. Both files are pure and unit-tested, every precedence case included.

## Palettes

`src/palettes.ts` holds the six brand palettes, taken from the brand package's `themes/themes.json`, with a light and a dark set each; `resolvePalette` falls back to Slate & Mint for an unknown key. How they reach the screen is described in [src/renderer/README.md](../../src/renderer/README.md).
